## 3. ⛔ 왜 못 했나 — **끄는 신호가 없다**

**켜는 쪽은 3차(`11fd8cb`)에서 풀렸다** — `.onDrag`는 끌기가 **실제로 시작될 때** 시스템이 부른다.
**막힌 것은 끄는 쪽이었고, `List`는 「지금 끌린다」를 안 알려준다.** 그래서 세 가지를 겹쳐 썼는데
**셋이 서로 다른 시점에 걸렸다:**

| 끄려던 것 | 언제 걸리나 | 왜 안 맞나 |
|---|---|---|
| `.onMove` | 순서가 **실제로 바뀔 때만** | 제자리에 놓으면 **안 불린다** |
| `.onDrop(isTargeted:)` | 드래그가 영역에 **드나들 때** | 손을 뗀 순간이 아니다 |
| **1.5초 안전망** | 끌기 시작 **1.5초 뒤** | **손을 떼기도 전에 걸린다** ← *"누르고만 있으면 … 사라지고"* |

**★ 1·2차는 켜는 쪽에서 깨졌고, 3차는 끄는 쪽에서 깨졌다.** 같은 요구의 반대편 끝이다.

**안전망은 원래 다른 증상을 막으려던 것이었다** — *"가만히 그 자리에서 손을 떼면 테두리가 안 없어져"*
(5초 → 1.5초). ⚠️ **그 땜질이 새 증상을 만들었다:** 5초일 땐 안 보이던
「누르고 있는데 꺼진다」가 1.5초로 줄이자 **정상 조작 시간 안으로 들어왔다.**

## 9. ★★ 잔상 — **재현했고, 고치는 길을 실측으로 찾았다**

### 9-1. ⛔ 먼저: 재설치해도 **여전했다**

`6973775`(`.onDrag` 없음)를 폰에 다시 얹고 사용자 판정: **"똑같이 잔상이 있음!"**
→ **`.onDrag` 범인설은 죽었다.** 그리고 「낡은 빌드였다」도 배제됐다(같은 코드를 두 번 얹었다).

### 9-2. ★ 못 재던 이유 — **조건을 놓치고 있었다**

사용자 말에 조건이 이미 있었다: *"**살짝 이동하면**"* · *"위 혹은 아래 항목과 **자리가 바뀌는 순간** 사라져."*
⛔ **잔상은 「첫 교체 전」 구간에만 있다.** 그런데 내 시험은 **셋째 줄까지 크게** 끌었다 —
**그 구간을 건너뛰고 찍고 있었다.** 끌기 거리를 **22pt**(한 줄보다 훨씬 작다)로 줄이자 **바로 나왔다.**

> ⚠️ **그리고 자동 판정기가 이것을 「없음」으로 읽고 있었다.** 잔상은 **흐리게** 그려져서
> 빨강 문턱(`r>200`)에 안 걸린다. **띠 개수는 1로 나왔고 실제로는 둘이었다.**
> → **눈으로 본 프레임이 판정을 뒤집었다.** 계측 규칙 4(「계산은 실측으로 닫는다」)의 같은 형태 —
> **자동 판정도 「계산」 쪽이다.**

### 9-3. 잰 값 — 같은 조건(22pt 끌고 12초 멈춤)

| 꼴 | 원래 자리 | 판정 |
|---|---|---|
| **F 복제** (SwiftUI `List` = 지금 앱) | **흐린 사본이 남는다** | ⛔ **잔상** |
| **G 복제+편집모드** (`editMode = .active`) | **똑같이 남는다** | ⛔ **잔상 — 편집모드는 답이 아니다** |
| **H UIKit** (`UICollectionView` + `beginInteractiveMovementForItem`) | **비어 있다** | ✅ **잔상 없음** |

**★ G가 중요하다** — 「편집 모드 버튼을 두면 된다」는 안이 **여기서 죽었다.**
SwiftUI `List`는 편집모드에서도 순서 바꾸기를 **드래그앤드롭으로** 돌리고, 그 길은
**첫 교체 전까지 원본을 흐리게 남긴다.** 손잡이만 얻고 잔상은 그대로다.

**H의 화면(`shots/I2_150.png`):** AAAA가 22pt 내려가 BBBB 첫 줄에 겹쳐 있고 **위는 비어 있다.**
F의 같은 프레임(`shots/G_150.png`)은 **흐린 AAAA + 밝은 AAAA 둘**이다.

### 9-4. ⚠️ H를 만들 때 밟은 함정 하나

`beginInteractiveMovementForItem`을 불러도 **아무 일도 안 일어났다.**
`UICollectionViewDiffableDataSource`는 **`reorderingHandlers.canReorderItem`을 켜야** 순서 바꾸기를 받는다.
⛔ **조용히 실패한다** — 오류도 로그도 없다. 켜자 바로 움직였다.

### 9-5. 그래서 남은 결정 — **값을 치를지**

**진짜 화면을 `UIViewRepresentable`로 바꾸는 것**이 유일하게 실측으로 통과한 길이다. 대가:

| 다시 만들어야 하는 것 | 메모 |
|---|---|
| 줄 눌러 상세로 가기 | 지금은 `NavigationLink`. UIKit 셀에서 직접 연결해야 한다 |
| 「대기」 캡슐 · 별 아이콘 · 흐림(0.55) · 다크 팔레트 | 셀 구성으로 옮긴다 |
| 머리글 두 줄 · **0개 밴드 숨김**(확인 ①-3) | 확인 목록에 있는 항목이다 |
| Dynamic Type · VoiceOver | `List`가 공짜로 주던 것 |
| **★ macOS** | `UIViewRepresentable`은 iOS 전용 — **맥 앱은 `List`를 그대로 둬야 한다**(`#if os(iOS)`로 갈린다) |

**공짜로 따라오는 것:** 끌 때 **자동 스크롤**은 `UICollectionView`가 해 준다(직접 만들 필요 없다).
**손잡이도 필요 없다** — 길게 누르기로 시작하므로 `30e2d91`에서 뺀 ≡를 되살리지 않아도 된다.

### 안 잃은 것

- **줄 모양은 SwiftUI 그대로** — `UIHostingConfiguration`에 넣었다. 색·글꼴·「대기」 캡슐·흐림(0.55)·
  Dynamic Type을 **다시 만들지 않았다.** ⚠️ 대신 **같은 모양이 두 곳에 있다**
  (`PrincipleReorderRow` = iOS · `PrincipleListView.row` = 맥) — **고칠 때 둘 다 고칠 것.**
- **끌 때 자동 스크롤**은 `UICollectionView`가 준다.
- **≡ 손잡이를 되살리지 않았다** — 길게 누르기로 시작하므로 필요 없다.

### 함정 둘 (주석에 남겼다)

1. **`reorderingHandlers.canReorderItem`을 안 켜면 `beginInteractiveMovementForItem`이
   조용히 아무것도 안 한다** — 오류도 로그도 없다. 랩에서 실제로 밟았다.
2. **스냅샷을 id로만 비교하면 안 된다** — 상세에서 문장을 고치고 돌아오면 **id는 같고 내용만 바뀐다.**
   순서만 보면 낡은 글이 남는다. → 순서 + 문장 + 동작 개수(N)를 **서명**으로 묶어 비교한다.

## 11. ㉣ 글자 크기 — **원인부터 쟀다** (`fa0f689`)

사용자 기준: **「새로운 기억」 탭 원칙 띠에 나오는 항목보다 2pt 크게.**
그리고 지시: *"먼저 왜 작아졌는지 짚어줘. 숫자만 키우면 증상은 사라지고 원인은 남는다."*

### 11-1. ⛔ 「`UIHostingConfiguration`이 줄인다」는 **아니었다 — 쟀다**

랩에 같은 글(`.callout.weight(.medium)`)을 **SwiftUI 직접**과 **셀 안**에 나란히 그리고,
`xcrun simctl ui … content_size`로 단계를 바꿔 가며 화면에 값을 찍었다:

| 단계 | SwiftUI 직접 | `UIHostingConfiguration` 셀 안 |
|---|---|---|
| L | `callout=16.0pt · trait=L · dts=large` | `callout=16.0pt · trait=L · dts=large` |
| XXL | `callout=20.0pt · trait=XXL · dts=xxLarge` | `callout=20.0pt · trait=XXL · dts=xxLarge` |

✅ **Dynamic Type는 안 끊겼다.** 셀이 트레잇을 그대로 받고, 단계를 올리면 셀도 같이 커진다.
✅ **셀 쪽에서 폰트·스케일을 덮고 있지도 않다** — 덮었다면 위 두 칸이 갈렸을 것이다.

### 11-2. 그러면 왜 작게 보였나 — **코드상 세 곳이 다 같은 글꼴이었다**

```
InboxView.swift:376            .font(.callout.weight(.medium))   ← 띠
PrincipleReorderList.swift:187 .font(.callout.weight(.medium))   ← 새 목록(iOS)
PrincipleListView.swift:107    .font(.callout.weight(.medium))   ← 목록(맥)
```
전역 덮어쓰기(`dynamicTypeSize`·`environment(\.font)`·`minimumScaleFactor`)도 **없다.**

> ⛔ **그래서 「작아지게 만든 기전」은 못 찾았다. 만들어 적지 않는다.**
> 잰 값으로는 **목록 = 띠**다. 남는 설명 둘:
> ① *"그것보다 작다"*의 **「그것」이 「띠+2pt」(목표치)**였다 — 그러면 전부 앞뒤가 맞는다.
> ② 띠는 **틴트 카드 + 좌우 14 / 상하 11 여백 + 굵은 번호**가 붙어 **더 커 보인다.**
>    새 목록은 카드가 없고 셀 여백이 **상하 6**이다. **글자 크기가 아니라 둘레가 다르다.**
> **어느 쪽이든 지금은 띠+2pt가 됐으므로 ㉣은 판정할 수 있다.**

### 11-3. 무엇을 넣었나 — `PrincipleFont.size`

**숫자(18)를 박지 않았다.** 단계마다 `.callout`의 **실제 크기를 읽어 +2** 한다.
그래야 접근성에서 글자를 키울 때 **이 목록만 안 커지는 결함**이 안 생긴다.
쓰는 쪽 두 뷰에 `@Environment(\.dynamicTypeSize)`를 하나씩 뒀다 — **단계가 바뀔 때 다시 그리는 의존**이다.

| 단계 | 띠(`.callout`) | 목록(+2) |
|---|---|---|
| L(기본) | **16** | **18** |
| XL | 18 | 20 |
| XXL | 20 | 22 |
| XXXL | 22 | 24 |

⚠️ **`@ScaledMetric(relativeTo: .callout) = 18`도 후보였는데 안 썼다** — 재 보니 차이가
**일정하지 않았다**(L +2.0 · XL **+1.7** · XXL **+1.3** · XXXL +2.0). 「2pt」는 모든 단계에서 2pt여야 한다.
