## 3. 조사 — 폰을 잃으면 무엇이 죽나

### 텍스트는 산다, 자료는 전부 죽는다

`find`로 iCloud 폴더 전수: **파일 16개 전부 `.md`/`.txt`/`.ps1`/`backups`.
`*.m4a`·`*.jpg`·`.icloud` 자리표시자 = 0개.**

`AudioStore`/`PhotoStore`의 `searchDirs()`가 로컬 하나만 반환한다. iCloud 경로는 **주석에만 있다.**
게다가 `project.yml`에 `UIFileSharingEnabled`·`LSSupportsOpeningDocumentsInPlace`가 없어
**파일 앱에서도 안 보인다** — 손으로 꺼낼 길이 없다.

### 실측 — 폰에만 있는 자료 **131개**

|---|---|---|---|---|
| 음성 `audio:` | **103** | 56 | 19 | **28** |
| 사진 `photo:` | **28** | 12 | 8 | **8** |
| 합계 | **131** | 68 | 27 | **36** |

**전부 `iphone-4532`가 만들었다**(다른 기기 0). 7월 55 · 8월 76.

### 용량 — 그때는 못 쟀고, 사용자가 재서 채웠다

세션 중에는 **「못 잼」으로 적었다** — 파일이 폰 샌드박스에 있어 맥에서 볼 수 없고,
사진 「200~500KB」는 설계 §4-③의 **목표치이지 실측이 아니며**, 음성은 코드가 AAC 비트레이트를

## 4. 잰 값 — iCloud 파일의 「이름은 있고 바이트는 없는」 상태

**01:06 · macOS 26.5.** iCloud Drive에 탐침 폴더를 만들고 `brctl evict` 뒤 Swift로 쟀다.
**탐침 폴더는 잰 직후 지웠다.**

```
fileExists(atPath:)     = true          ← ⚠️
downloadingStatus       = NotDownloaded
fileSize                = 66
totalFileAllocatedSize  = 0
contents(atPath:)       = 66 bytes      ← macOS는 읽을 때 투명하게 받아온다
```

**지금 `url(forId:)`의 판정이 `fileExists` 하나다.** iCloud를 `searchDirs()`에 더하는 순간
**바이트가 없는 파일에도 URL을 돌려준다** → 설계 §4에서 세 갈래 판정으로 바꾸는 근거.

⚠️ **macOS에서 잰 값이다. iOS는 못 쟀다.** 폰에서 재려면 탐침 빌드가 필요하다.

### 못 잰 것 하나 — 하위 폴더 생성

보안 스코프 북마크가 **하위 디렉터리 생성**에 닿는지는 **안 재봤다.**
맥 앱은 App Sandbox entitlement가 없어 **대조군이 못 된다.**
문서상으로는 될 것으로 보지만 **추정이다** → **구현 첫 걸음으로 넘겼다**(사용자 결정 ㉠).

## 5. 조사 — 완전 삭제 · iCloud 배선 · macOS

### 완전 삭제는 코드가 0줄

`ArchiveView`의 스와이프는 **「되돌리기」 하나뿐**. 파일 머리주석이 직접 적고 있다:
*"(완전 삭제는 edit-policy.md §8 보류 — 엔진 hard-delete + 재확인 확정 후.)"*
`edit-policy.md` §8은 **「삭제·완료 세부 정책: 이번 문서 이후 계속 논의」**에서 멈춰 있다.

**확정된 자료 파일을 지우는 코드도 0줄** — `removeItem`은 전부 임시 파일용(`deleteTemp`).

**tombstone과 append-only가 부딪히는 자리 셋:**
① `delete`는 이벤트 한 줄일 뿐 → 이벤트가 살아 있는 한 항목은 영원히 존재
② `EventWriter`가 내는 verb 다섯에 **「지운다」가 없다**
③ ⚠️ **반쪽 삭제는 유령을 만든다** — `MergeEngine.merge`는 이벤트를 id로만 묶고
   **create 블록이 있는지 확인하지 않는다.** create만 지우면 `raw` 없는 빈 줄이 보관함에 남는다.
④ 전례는 있다 — `2026-08-18-strip-auto-fields.py`가 조각 파일을 다시 썼다. **다만 그건 맥에서 파이썬으로** 한 것이고,
   **다른 기기가 옛 사본을 들고 있으면 되살아난다.**

### iCloud 배선 — 이음매가 하나

`FragmentFolder`는 **iCloud entitlement를 안 쓴다.** 문서 피커로 고른 폴더의 **보안 스코프 북마크**뿐이다.
`searchDirs()`가 유일한 이음매이고, 두 저장소 주석이 이미 그 확장을 예고하고 있다.

**write-once가 결정적으로 유리하다** — 파일명이 id에서 결정적으로 나오고 한 번 쓰고 안 고치므로
**충돌 해소가 필요 없다.** 조각 파일 분리도 불필요.
⚠️ **삭제가 생기면 이 유리함이 반쯤 사라진다**(「없는 파일」이 *안 받은 것*인지 *지운 것*인지 갈려야 하므로).

**부분 다운로드는 이미 쓰고 있다** — `FragmentFolder.read()`가 `startDownloadingUbiquitousItem`을 부른다.

### macOS — 음성은 이미 되고, 사진만 막혀 있다

**macOS 타깃 빌드: `EXIT=0` · error 0** (오늘 확인).

| | macOS에서 지금 |
|---|---|
| 아이콘·「있음」 표시 | ✅ 된다 (필드 유무만 봄) |
| **원본 음성 재생** | ✅ **파일만 있으면 코드 0줄** — `audioRow`가 `#if os(iOS)`로 안 감싸져 있다 |
| 사진 보기 | ⛔ `photoRow`가 `#if os(iOS)` (`UIImage`) |
| 촬영 | ⛔ iOS 전용 |

### 조사 중에 나온 것 — 포인터 필드가 조회에 안 쓰인다

`audio:`/`photo:`를 읽는 자리 넷이 **전부 「nil인가」만 본다**(`DetailView:340·341·432·433`).
실제 파일은 `filename(forId: id)`가 **id에서 계산**한다. **포인터 필드는 지금 사실상 불리언이다.**

**→ 이것이 순서 판단의 핵심 근거가 됐다.** 「어디를 뒤지나」(위치)와 「무엇을 뒤지나」(확장)가
**코드에서 서로 다른 이음매**라서, 위치를 먼저 옮겨도 두 번 만지는 것이 거의 없다.

### 「받는 중」이 왜 갈려야 하나 — 새 원칙이 아니다

`FolderLink.swift` 머리주석이 이미 세워 둔 원칙이다:
*"연결이 끊긴 것과 비어 있는 것을 절대 같게 보이지 않는다. … 파일은 iCloud에 그대로 있는데
사람은 그것을 알 방법이 없어 그 순간 앱을 지웠다 깔 수도 있다."*
**자료도 똑같은 모양이다.** 「없다」와 「아직 안 받았다」를 뭉치면 같은 일이 일어난다.

### ★ 「받는 중」은 폰에서 안 나온다

로컬 사본이 있으니 폰은 항상 「여기 있다」다. **그 상태를 만나는 것은 Mac이고, 검증도 거기서 한다.**
(사용자가 짚은 것 — 판정표 §10에 반영했다.)

## 8. 이 세션에서 잘못했던 것 하나

`AskUserQuestion`으로 문구를 물었는데, **사용자 지시문이 세 번 잘려서 들어온 상태**였다.
사용자가 *"중간에 자료가 끊겨서 여러 번에 걸쳐 답을 준 것이 혼란스럽다"*고 해서 **처음부터 다시 받았다.**

**교훈:** 지시문이 잘린 것을 알았으면 **부분 답을 쌓지 말고 온전한 지시를 먼저 기다리는 편이 낫다.**
잘린 채로 답을 세 번 나눠 주면 **무엇이 최신인지 사람 쪽에서 헷갈린다.**
