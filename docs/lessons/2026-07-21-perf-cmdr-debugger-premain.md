# Lesson — "앱이 느리다"의 진짜 원인은 Xcode ⌘R 디버거였다 (2026-07-21)

> 규칙화: `CLAUDE.md` §"성능 측정 규칙 (실사용 조건에서 잰다)". 이 문서는 그 규칙이 나온 배경·전말이다.

## 증상
- 새로 설치(Xcode 빌드)하면 **첫 실행이 ~10.8초**, STT **"듣는 중…"도 ~5초**.
- 앱을 위로 스와이프해 종료 후 다시 켜면(홈 탭) **즉시**. 전원 재부팅 후 첫 실행은 ~2초, 그 뒤 빠름.
- 즉 **"새 설치의 첫 실행만" 느림.** 실사용(홈 탭)엔 느림 없음.

## 잘못된 가정들 (헛짚은 순서)
1. "어제 STT·비동기 로드 변경이 느리게 만들었다" — 체감 A/B로 "B가 느리다"처럼 보였으나 **순서효과(늘 B를 A 삭제 직후 두 번째로 설치) confound**.
2. "재설치 첫 실행 = iOS 설치 페널티(코드 무관)" — 근거 부실. 사용자가 "예전엔 수없이 리빌드해도 이런 적 없었다"고 정확히 반박.
3. "처음 보는 새 cdhash의 첫 실행 비용" — devicectl로 **새 cdhash도 빠름**으로 반증.
4. (더 거슬러: '조율-읽기' → '온디바이스 모델 로드'로도 두 번 헛짚음.)

## 진짜 원인
- **Xcode ⌘R = Debug 구성 빌드 + lldb 디버거 attach.** 범인은 Debug 구성이 아니라 **디버거 attach의 pre-main 비용**.
- 계측: ⌘R로 **premain(프로세스 시작→App.init) = 9.8초**. 같은 앱을 devicectl(디버거 없음)로 = **62ms**. **158배 차이.**
- **버전 무관 확정**: baseline A(`13caaa9`) ⌘R premain **9803ms** ≈ 어제 코드 B(`321001f`) **9826ms**.
- **STT도 동일**: 디버거 없이 홈 탭으로 하니 "듣는 중" 지연 **재현 안 됨**.
- **결론**: 두 증상 다 개발환경(이 기기/iOS 26/현 Xcode) ⌘R 디버거 아티팩트. 배포·실사용(홈 탭/TestFlight/App Store) 무관.

## 해결에 든 노력
- **10시간+**, 위 4단계로 여러 번 헛짚음. 계측 코드(LaunchTimer, premain sysctl) 두 번 심었다 걷어냄, 재빌드·재설치 수십 회.
- 도구 삽질: `DYLD_PRINT_STATISTICS`는 iOS 26에서 출력 안 됨. `log --device`는 이 macOS에서 미지원(+ zsh `log` 함수 충돌) → `devicectl process launch --console`(stderr)로 우회.

## 핵심 교훈
1. **추측하지 말고 계측하라.** A/B를 **같은 조건에서 숫자로** 비교하니 "코드 무관"이 한 번에 드러났다(baseline premain ≈ 현재 premain).
2. **측정 조건이 결과를 지배한다.** 디버거 유무 하나로 **62ms ↔ 9.8초**. 반드시 **실사용 조건(디버거 없이, 홈 탭)**에서 재라.
3. **단발·오염된 측정으로 단정하지 마라.** 중간에 "탭하니 즉시"라던 측정도 직전 `devicectl` 실행으로 검증이 데워진 confound였다.
4. **사용자의 "예전엔 안 그랬다"를 무시하지 마라.** 그 반박이 안이한 "설치 페널티" 결론을 무너뜨리고 진짜 원인으로 이끌었다.
