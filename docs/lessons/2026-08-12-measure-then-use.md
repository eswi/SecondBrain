# 교훈 — 재는 법이 아니라 **가져다 쓰는 법**이 틀렸다 (2026-08-10 ~ 08-12, 맥미니)

## 한 줄
상세 화면 압축을 계측으로 몰고 가면서 **나흘에 네 번** 숫자를 틀렸다.
**네 번 다 재는 것은 맞았다.** 틀린 것은 **잰 값을 쓰는 단계**였고, 네 번이 **서로 다른 단계**였다.
그래서 넷을 나란히 두면 형태가 보인다 — `CLAUDE.md` 「계측 규칙」의 네 조항이 **이 넷과 1:1로 맞는다.**

## 넷을 나란히

| | 날 | 어느 단계에서 틀렸나 | 무엇을 했나 | 대가 |
|---|---|---|---|---|
| **①** | 08-10 | **조립** | `menuRow`의 간격 20pt를 **줄마다 세지 않고 한 번만** 셌다 | 폭 셋을 낙관적으로 적고 **결론이 틀렸다** — 「제목을 줄이면 337pt로 겨우 들어간다」(실제 365.1, 23pt 넘침) |
| **②** | 08-12 | **딱지** | 계측표의 **폭 값**(`photo @12pt = 17`)을 **높이에** 갖다 썼다 | 카드 높이를 96.8로 계산(실제 92) |
| **③** | 08-12 | **상수** | Dynamic Type 크기를 **기억으로** 썼다(XXXL을 20pt로 — 실제 **23pt**) | 위험 임계를 XXXL로 적었다. **실제로는 XXL(21pt)부터** 넘쳤고 폭도 2.5pt가 아니라 **8.8pt**였다 |
| **④** | 08-12 | **닫기** | **「계측 규칙」을 만든 그날** 「92 ≈ 92로 맞는다」를 **계산만으로** 결론냈다 | 두 카드 밑변이 3.3pt 어긋났고 **사용자가 화면에서 바로 알아챘다** |

**★ 넷이 같은 실수의 반복이 아니다.** ①은 합칠 때, ②는 값의 종류를 볼 때, ③은 값을 가져올 때, ④는 결론을 낼 때다.
「조심하자」로는 안 잡힌다 — **단계마다 다른 관문이 필요하다.** 그것이 규칙 네 조항이 된 이유다.

| 틀린 단계 | 규칙 |
|---|---|
| ① 조립 | **조립을 검산한다** — 요소 폭 + **요소마다의** 간격. 한 줄 공식을 여러 줄에 재사용할 때 간격을 한 번만 세기 쉽다 |
| ② 딱지 | **계측값에 「폭/높이」 딱지를 붙인다** — 심볼은 폭≠높이이고 **심볼마다도 다르다** |
| ③ 상수 | **상수는 기억으로 쓰지 말고 그 자리에서 확인한다** — 폰트 크기, Dynamic Type 단계, 권장 표적 44pt, 심볼 치수 |
| ④ 닫기 | **계산은 후보를 좁히는 데 쓰고 결론은 실측으로 닫는다** |

## ★ ④가 가장 값진 것이었다 — 규칙을 적는 것과 지키는 것은 다르다

①②③를 겪고 **그날 「계측 규칙」을 CLAUDE.md에 올렸다.** 그리고 **같은 날** ④를 했다.
규칙 4번(「결론은 실측으로 닫는다」)을 직접 써 놓고, 몇 시간 뒤 「92 ≈ 92」를 계산으로 냈다.

**→ 규칙은 「알고 있음」으로 지켜지지 않는다. 관문이 실제 절차 안에 있어야 한다.**
그래서 도구를 저장소에 넣었다(아래) — **재는 것이 쓰는 것보다 쉬워야** 규칙이 지켜진다.

## 곁가지 하나 더 — 편향이 한쪽이었다

계산이 실측보다 **일관되게 2~3pt 낙관적**이었다(항상 실제가 더 넓거나 컸다):

| | 계산 | 실측 |
|---|---|---|
| 「주차 위치 ⌄」 | 77.2 | **78.6** |
| 「아이디어 ⌄」 | 72.9 | **74.7** |
| 성역 접힘 카드 | 93.9 | **95.0** |
| 분류 접힘 카드 | 92.2 | **91.7** |

방향이 한쪽이면 **여유를 그만큼 깎아서 봐야 한다.** 여유가 10pt 남는다고 적었으면 실제로는 7~8pt로 읽을 것.

## 도구 — `native/tools/`

| 도구 | 무엇을 재나 |
|---|---|
| **`measure-text.swift`** | 글자 폭·줄높이(CoreText) · SF Symbol **폭 x 높이**. 폭/높이를 **함께** 찍어 ②를 막는다 |
| **`measure-ui.swift`** | 스크린샷 픽셀에서 **카드·블록 경계**. 결론을 닫는 데 쓴다(④) |

**왜 `docs/`가 아니라 `native/tools/`인가:** 실행하는 것이고(문서가 아니다), 재는 대상이 **네이티브 앱 UI**다.
`sb-migrate`가 이미 그 자리에 있다. 그리고 **기기를 넘어야 하니 저장소에** 둔다 —
`/tmp`에 두면 다음 계측 때 또 만들고, 맥북에서는 아예 없다(「기록 규칙」의 그 이유).

### 시뮬레이터에서 재는 법 — 픽셀이 접근성 좌표보다 낫다
접근성 좌표(AppleScript/System Events)로도 위치·크기를 읽을 수 있고 **`342 × 14pt` 같은 표적 크기는 그것으로 잡았다.**
그런데 두 가지로 막혔다: ⓐ **작업 중 시뮬레이터 창이 움직이면** 좌표가 통째로 어긋난다
ⓑ 같은 화면에서 **트리 읽기가 성공/실패를 반복**한다. → **픽셀 측정은 창 위치와 무관하고 실패하지 않는다.**

### ⚠️ 아직 안 잰 것 — Dynamic Type 단계 크기
이 문서의 **L 17 / XL 19 / XXL 21 / XXXL 23**은 애플이 공표한 표를 쓴 것이고 **내가 잰 값이 아니다.**
③과 같은 종류의 위험이 남아 있다는 뜻이다. **재는 길이 있다:**

```
xcrun simctl ui booted content_size extra-extra-large   # 단계를 바꾼 뒤
swift native/tools/measure-ui.swift <스크린샷> <x열>     # 실제 렌더를 잰다
```

→ 2단계 착수 전에 이걸로 **단계별 실측**을 하면 ③의 뿌리가 닫힌다.

# ★ 덧붙임 (2026-08-12 맥북) — 도구를 쓰니 함정이 「값을 읽는 쪽」으로 옮겨왔다

이 문서를 쓴 그날 오후, 회사 맥북에서 **도구 둘로 Dynamic Type 9단계를 실측**했다.
**어제의 넷은 한 번도 안 났다.** 대신 **새 함정 넷**이 났고, 넷 다 `measure-ui.swift`를 쓰는 쪽이었다.

| | 무엇을 했나 | 신호 |
|---|---|---|
| ⑤ **모서리** | 카드 둥근 모서리 안쪽 열로 재서 **짧게** 읽었다 | 열마다 값이 조금씩 달랐다(92.3/93.7/94.3/95.0) |
| ⑥ **배경 뒤바뀜** | XXXL에서 카드가 화면 끝까지 붙어 **기본 배경 표본(x=15)이 카드 안**에 들어갔다 | **글자를 키웠는데 원문 카드가 88.0→40.0pt로 줄었다** |
| ⑦ **`--bg`를 카드 위에** | ⑥을 고치려다 배경 점을 카드 표면에 찍었다 | 출력 밝기가 0.1127(카드)이었다. 배경은 0.0744 |
| ⑧ **창 끝을 카드 끝으로** | `--y` 창에서 잘린 구간을 카드 높이로 적었다 | 구간 끝값이 `--y` 끝값과 **같았다** |

**⑧이 가장 나빴다 — 「못 잰 것」을 「잰 것」으로 적었다.**
AX5 성역 카드를 **「≈393pt」** 로 적었는데, 실제로는 **하단 바에 가려 밑변이 화면에 없어 잴 수 없는** 카드였다.
말할 수 있는 것은 **「최소 381pt 이상」** 뿐이다.

**어떻게 잡았나 — 사용자가 화면을 보고 「AX4·AX5가 너무 커 보인다」고 했다.**
다시 재보니 성역 구간이 이미지 맨 아래까지 끊기지 않았다(카드→하단 바→탭바가 배경 없이 붙어 있다).
**④(「결론은 실측으로 닫는다」)를 지켰다고 생각한 자리에서 ⑧이 났다** — 화면을 잰 것은 맞는데,
**잰 값이 유효한지를 안 본 것**이다. 그래서 처방이 하나 더 붙는다:

> **⑧의 처방 — 값이 유효한지 먼저 보고 적는다.** 구간 끝 == `--y` 끝이면 잘린 값이다.
> 창을 넓혀 다시 재고, 넓혀도 이미지 끝에 닿으면 **「못 잼」으로 적는다. 값을 만들지 않는다.**

넷의 전문은 `native/tools/measure-ui.swift` 머리주석에 있다(쓸 때 바로 보이는 자리).

## ★ 정정 — 「92 vs 95 · 3.3pt 어긋남」은 지금 사실이 아니다

이 문서 ④와 「편향」 표가 **성역 접힘 95.0 / 분류 접힘 91.7 → 밑변 3.3pt 어긋남**을 적고 있다.
**2026-08-12 실측: 접힘에서 두 카드는 높이·밑변이 정확히 같다(어긋남 0pt).**
Large 95.0 / XL 102.3 / XXL 109.3 / XXXL 116.3pt — **네 단계 모두 위·아래가 픽셀 단위로 동일**하다.
**`e01b041`(1-A 분류 카드를 세로 배치로)이 없앤 것으로 보인다.**

**옛 값은 지우지 않는다.** 그때의 판단 근거였고, **무엇이 언제 바뀌었는지는 그 대비로만 보인다.**
(같은 정정을 `native/Sources/App/DetailView.swift`의 `metaTypeRow` 주석에도 달았다.)

⚠️ **다만 「계산이 실측보다 2~3pt 낙관적」이라는 편향 자체는 이 정정으로 뒤집히지 않는다** —
그 표의 네 항목 중 셋은 접힘 밑변과 무관한 폭 값이다. **편향은 그대로 여유를 깎아서 볼 것.**
