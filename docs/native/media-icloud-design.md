## 0. 왜 — 지금은 폰을 잃으면 자료를 전부 잃는다

**2026-08-19 조사(맥미니)에서 확인한 것:**

| | 지금 |
|---|---|
| 텍스트 | ✅ **산다.** 폰 조각 `inbox-iphone-4532.md`가 iCloud Drive에 있고 동기화된다 |
| **자료(음성·사진)** | ⛔ **전부 죽는다.** 앱 샌드박스 `Application Support/SecondBrain/{audio,photo}/`에만 있다 |

`AudioStore.searchDirs()`·`PhotoStore.searchDirs()`가 로컬 하나만 반환한다. iCloud 경로는 **주석에만 있고 코드엔 없다.**
게다가 `project.yml`에 `UIFileSharingEnabled`도 `LSSupportsOpeningDocumentsInPlace`도 없어 **파일 앱에서도 안 보인다** —
손으로 꺼낼 길이 없다.

**iCloud 기기 백업은 켜져 있다**(2026-08-19 확인). 완전 무방비는 아니다. 다만 **기기 통째 복원 전용**이라
파일 하나를 꺼낼 수 없고, 마지막 백업 이후분은 사라진다. **위험이 닫힌 것이 아니다.**

**이번 목적 = 분실 대비.** 그리고 자료의 종류·수가 늘고 수정·삭제가 생기므로 **Mac에서도 쓸 수 있어야 한다.**

## 0-B. 잰 값 — iCloud 파일의 「이름은 있고 바이트는 없는」 상태

**2026-08-19 01:06 · 맥미니 macOS 26.5.** iCloud Drive에 파일을 만들고 `brctl evict`로 실체를 걷어낸 뒤 쟀다:

```
fileExists(atPath:)     = true          ← ⚠️ 여기가 함정
downloadingStatus       = NotDownloaded
fileSize                = 66            ← 논리 크기는 안다
totalFileAllocatedSize  = 0             ← 바이트는 없다
contents(atPath:)       = 66 bytes      ← macOS는 읽는 순간 투명하게 받아온다
```

**지금 `url(forId:)`의 판정이 `fileExists` 하나다.** iCloud를 `searchDirs()`에 더하는 순간
**바이트가 없는 파일에도 URL을 돌려준다.**

⚠️ **이건 macOS에서 잰 값이다. iOS는 못 쟀다.** macOS는 dataless 파일을 읽는 순간 투명하게 받아오지만
iOS가 같은지는 확인 못 했다 — 그래서 `FragmentFolder`가 `startDownloadingUbiquitousItem`을 먼저 부르는 것으로 보인다.
**폰에서 재려면 탐침 빌드가 필요하다.**

## 2-A. 자리 로그 `.sb-media.log` (2026-08-19 사용자 결정 · 구현됨)

**왜 있나:** 구현을 B안(자리 계산을 「iCloud 자리를 계산하는 함수」에 넣고 업로더 첫 실행이 답이 된다)으로
가기로 하면서 사용자가 조건 하나를 걸었다 — **그 시도가 첫 실행에 묻혀 있어서, 조용히 폴백으로 넘어가면
이번 걸음의 답을 못 본다.** 그래서 **성공이든 실패든** 남긴다.

> **맥에서 셋이 갈려야 한다:** 「폴더가 있다」 · 「만들려다 실패해서 루트로 갔다」 · 「아직 아무것도 안 올라감」.

> ### ★ 원칙 — **로그는 예상과 다른 것만 적는다. 정상이면 0줄.**
> 자리 로그의 「바뀔 때만」과 **같은 모양**이고, 업로드 로그의 「실패만」(§5)도 이것이다.
> **왜:** 정상까지 적으면 파일이 자라 **진단용인데 진단이 안 된다.** 그리고 잘된 것은 대개
> **결과 그 자체가 증거**다 — 올라간 파일은 iCloud 폴더에 보이므로 「올렸다」는 줄이 중복이다.
> **정상이 0줄이면 줄이 하나라도 있는 것 자체가 신호가 된다.**

| | 정한 것 | 근거 |
|---|---|---|
| 자리 | iCloud 폴더 루트의 **숨김 파일 `.sb-media.log`** | 폰 샌드박스는 맥에서 못 읽으므로 이 폴더 안이어야 한다. 숨김이면 **파일 앱에 안 보여** `inbox*.md` 옆이 안 지저분해진다 — `audio/`·`photo/`를 하위에 두는 것과 **같은 이유**. 같은 폴더의 `.DS_Store`·`.claude/`가 이미 동기화되는 것을 확인했다(숨김도 iCloud를 넘어온다) |
| 빈도 | **바뀔 때만** (첫 실행 포함) | 실행마다면 켤 때마다 줄이 늘어 몇 주면 「자리가 어디로 정해졌나」를 읽을 수 없다. **진단용인데 진단이 안 된다.** 바뀔 때만이면 **파일 자체가 상태를 말한다** — 두 줄이면 정상, 세 번째 줄이 있으면 그때 무슨 일이 있었다 |
| 실패 원인 | **`err=<domain>/<code>` — 시스템이 준 값 그대로** | 해석을 붙이지 않는다. 오류와 원인의 대응이 문서로 보장되지 않아 **추측을 문장으로 만들면 틀린다**(`FolderLink.unreachable` 주석이 세운 경계). 원인이 아예 없으면(같은 이름의 **파일**이 있는 경우 등) **칸을 비운다 — 값을 만들지 않는다** |

```
2026-08-19T12:10:33+09:00 iphone-4532 audio place=subdir      ← 정상
2026-08-19T12:10:33+09:00 iphone-4532 photo place=subdir
2026-08-20T13:02:11+09:00 iphone-4532 audio place=root err=NSCocoaErrorDomain/513   ← 폴백으로 넘어간 순간
```

**세 상태를 읽는 법 (맥에서):**

| 맥에서 보이는 것 | 뜻 |
|---|---|
| `place=subdir` + `audio/`·`photo/` 디렉터리 | ㉠ **성공** — 하위 폴더가 된다 |
| `place=root` (+ `err=…`) | ㉠ **실패** — 루트 폴백. **§2의 「폴백 기록」 칸을 채운다** |
| `.sb-media.log`가 없다 | **아직 앱이 그 폴더를 못 썼다** — 시도조차 안 된 것 |

**어디에 있나:** 판정·형식 = `MediaPlace.swift`(Core, 시험 17개) · I/O = `MediaCloud.swift`(App).
**도는 시점** = 폴더를 쓸 수 있을 때의 매 로드(`FolderLink.canCapture`) — §3의 업로더가 붙는 자리와 같다.

### ⚠️ 미결 — 보안 스코프의 수명 (단계 5에서 정한다)

**지금 `FragmentFolder.withFolder`는 스코프를 열고 함수가 돌아올 때 닫는다.** 그런데 iCloud 경로의 파일을
**재생·표시하는 동안**은 스코프가 열려 있어야 한다. 즉 **파일을 찾아 URL을 돌려주는 것만으로는 부족하다.**

- **폰에서는 안 걸린다** — 로컬 사본이 있어(§5) 재생은 항상 로컬 URL로 간다.
- **Mac에서 걸린다** — 거기서는 iCloud가 유일한 사본이고, **§7(Mac 사진 보기)이 이번 범위다.**
- **지금 정하지 않는다**(사용자 결정 2026-08-19): 실물을 안 보고 정하는 것이 된다. **단계 5에서 정한다.**
- ⚠️ 이 줄이 없으면 **거기까지 가는 동안 잊힌다** — 그래서 대화가 아니라 여기에 적는다.

## 3. 언제 올리나 — 수집 경로는 iCloud를 안 건드린다

### ⛔ `finalize()`의 목적지를 바꾸면 안 된다

```swift
// InboxModel.capture — 지금 코드
if let audioTemp, let name = AudioStore.finalize(temp: audioTemp, forId: id) {
    extra["audio"] = name       // ← 실패하면 이 줄이 안 돈다
}                                //    그리고 항목이 음성 없이 만들어진다
```

`finalize`가 nil이면 **항목은 그냥 음성 없이 생성된다**(graceful — 의도된 동작).
목적지를 iCloud로 바꾸면 **네트워크가 느리거나 끊긴 순간 원본 음성이 영구 유실된다.**
「자료 유실이 최우선」과 정면으로 부딪힌다.

### → 두 단계로 가른다

| | 하는 일 | 실패하면 |
|---|---|---|
| **① 확정** *(지금 그대로 · 변경 없음)* | 임시 → **로컬** `<id>.m4a` | 로컬 쓰기는 실패할 이유가 거의 없다 |
| **② 올리기** *(새로 만드는 것)* | 로컬 → iCloud **복사.** 원본은 남는다 | **다음 실행이 다시 집는다.** 원본은 로컬에 그대로 |

- **② 도는 시점:** 앱 시작 · 캡처 저장 직후 · 포그라운드 복귀.
- **대상 계산:** 「로컬에 있는데 iCloud에 없는 것」을 **매번 새로 뺀다.**
  **상태를 저장하지 않으므로 멱등**이고, 도중에 죽어도 다음 실행이 이어간다.
- **원자성:** iCloud 쪽에 임시 이름으로 복사 → **같은 폴더 안에서 rename**(같은 볼륨 rename은 원자적).
  **반쯤 올라간 파일이 제 이름으로 보이는 일이 없다.** 남은 찌꺼기는 다음 실행이 치운다.
- **쓰기 방식:** `FragmentFolder.appendLine`과 같은 `NSFileCoordinator` 패턴.
- **폴더 미선택이면 안 돈다** — 그 상태에선 텍스트도 안 되므로 앱이 이미 안내 화면을 띄운다(`FolderLink`). 일관된다.

| `MediaUploader.plan()` (App) | 찌꺼기 청소 → **한도 판정을 먼저 잰다** → 차집합 → 한도 적용 |
| `MediaUploader.upload(_:)` | 같은 폴더에 `sb-uploading-<id>.<ext>`로 복사 → **rename**. 실패면 찌꺼기를 지우고 로그 한 줄 |
| `MediaUploadJudge` (Core) | 한도(`cloudMediaCount == 0` → 5) · 「나머지가 남았나」. 시험 10개 |
| `InboxModel.migrateMedia()` | 매 로드마다 · 겹쳐 도는 것 방지 · I/O는 전부 메인 밖(순수 값만 돌려받는다) |

**두 가지를 못박아 뒀다 — 어기면 조용히 틀린다:**

1. **「이미 올렸나」는 이름으로만 본다. 바이트를 보지 않는다.**
   iCloud가 실체를 걷어낸(evict) 파일도 **올라간 것**이다. 바이트로 판정하면 맥에서 evict된 순간
   **131개를 영원히 다시 올린다.**
2. **첫 실행 5개는 종류를 번갈아 고른다.** 음성 103 · 사진 28이라 그냥 이어붙이면 **첫 5개가 전부 음성**이 되고
   **`photo/`가 만들어지는지 못 본다.** 한도를 5로 정한 근거가 *"양쪽에 파일이 생기는지 보기 충분하다"* 였다.

⚠️ **매 로드마다 돈다** — 포그라운드 복귀·행동 뒤 재로드에도 차집합을 다시 계산한다(멱등하므로 안전).
다 올라간 뒤에는 `fileExists` 확인이 자료 수만큼 돌 뿐이고 **메인 밖**이다. 실제 비용은 **안 쟀다.**

## 4. 어떻게 찾나

```
찾는 순서 = [ 로컬 , iCloud ]
```

**로컬이 먼저인 이유:** 로컬은 **바이트가 반드시 있는 층**이다. iCloud는 이름만 있을 수 있다(0-B).

**중복은 정상이고 해소가 필요 없다.** 원본은 **write-once·불변**이라 같은 id의 두 사본은
**내용이 같은 것이 보장된다**(`edit-policy.md` §6). 첫 히트를 쓴다.

### 판정을 `fileExists`에서 떼어낸다

지금 `url(forId:)`는 **URL 아니면 nil** — 두 값으로는 세 상태를 못 담는다. 세 갈래로 답하게 바꾼다:

| 답 | 뜻 | 화면 |
|---|---|---|
| **여기 있다** | 바이트가 있다 (로컬이든, 내려온 iCloud든) | 재생 버튼 · 사진 |
| **아직 안 받았다** | iCloud엔 있는데 실체가 없다 | 받기 시작 + 「원본 음성 받는 중…」 ← **새로 생기는 상태** |
| **어디에도 없다** | 이 기기에도 iCloud에도 없다 | 지금 문구 그대로(「원본 음성 있음 · 이 기기엔 없음」) |

**포인터 필드는 안 건드린다.** `audio:`/`photo:`는 create 블록에 찍힌 **성역**이고,
파일명이 `<id>.m4a`로 그대로이므로 **값이 안 바뀐다.**

### 구현됨 (2026-08-19 · 단계 2) — 그리고 **예고와 달라진 것 하나**

| 자리 | 무엇 |
|---|---|
| `MediaAvailability` + `MediaAvailabilityJudge` (Core) | 세 갈래 판정. 시험 7개 |
| `MediaCloud.cloudFacts`/`readableURL`/`candidates` (App) | 사실 수집 — 이름이 있나 · **바이트가 있나** |
| `AudioStore.availability(forId:)` · `PhotoStore.availability(forId:)` | 세 갈래를 화면에 줄 자리(화면 연결은 단계 4) |
| `url(forId:)` | 로컬 → **바이트가 있는 iCloud**. 이름만 있는 파일은 안 돌려준다 |

> ### ⚠️ **iCloud는 `searchDirs()`에 안 들어갔다** — 옛 예고가 뒤집혔다
> `AudioStore`/`PhotoStore`의 머리주석과 이 문서 §0-B는 *"iCloud를 `searchDirs()`에 더하는 순간"* 이라고
> 적고 있었다. **그 방식으로는 안 된다:** iCloud 쪽은 **보안 스코프를 열어야** 보이고
> **자리(하위 폴더/루트)를 먼저 계산**해야 해서 **URL 목록에 담기지 않는다.**
> 그래서 `searchDirs()`는 **로컬 전용으로 남고**, iCloud는 `MediaCloud`가 따로 본다.
> **유지되는 것:** 찾는 순서 **[로컬, iCloud]** · 로컬 우선의 이유 · 중복 허용 · **포인터 필드 불변.**
> (코드 머리주석 둘도 같은 날 「뒤집혔다」로 고쳤다 — 지우지 않고 옛 서술과 함께 남겼다.)

**바이트가 있나를 어떻게 재나:** `ubiquitousItemDownloadingStatus`가 `.notDownloaded`가 **아닌지**로 본다.
키가 없으면(iCloud 항목이 아니면) `totalFileAllocatedSize > 0`으로 본다 — §0-B에서 dataless는 **0**이었다.
⚠️ **`fileExists`로는 절대 못 잰다**(§0-B: dataless도 true).

## 5. 기존 131개 — 별도 이관 코드가 없다

> ### ★ 131개 이관 = §3 업로더의 **첫 실행**이다.

대상이 「로컬에 있는데 iCloud에 없는 것」이므로, 처음 켤 때 그 목록이 **정확히 131개**다.
일회성 마이그레이션을 따로 만들면 **같은 코드를 두 번 쓰는 것**이 된다.

| | 답 | 근거 |
|---|---|---|
| 일회성인가 켤 때마다인가 | **켤 때마다** | 이관·신규·재시도가 한 코드로 처리된다 |
| 도중에 끊기면 | **다음 실행이 남은 것만 집는다** | 대상을 상태가 아니라 **두 폴더의 차집합**으로 계산 |
| 옮긴 뒤 로컬 사본 | **남긴다** | 아래 |
| 진행 표시 | **목록 위 배너** · 「자료 옮기는 중 · 12/131」 | §8 |
| **첫 실행 한도** | **5개** (iCloud 쪽이 0개인 실행만) | 아래 |

### 첫 실행 한도 — **5개** (2026-08-19 사용자 결정)

**iCloud 쪽 자료가 0개인 실행만 5개까지 올리고 멈춘다.** 그 뒤 실행부터 전량.

| | |
|---|---|
| 왜 한도가 있나 | **확인 지점을 한 번 만든다** — 이 첫 실행이 확인하려는 것은 **「올라가는가」와 「어디에 올라가는가」**이지 처리량이 아니다. 5개면 `audio/`·`photo/` 양쪽에 파일이 생기는지 보기 충분하고, **잘못됐을 때 치울 것이 5개뿐**이다 |
| 왜 이 꼴인가 | **상태 저장이 0이다 — 상태가 iCloud 폴더 그 자체다.** 「첫 실행인가」를 어디에도 안 적고 「iCloud 쪽이 0개인가」로 안다. **차집합으로 대상을 계산하는 것과 같은 방식**이고 멱등이 안 깨진다 |
| 왜 「한 실행에 최대 N」이 아닌가 | 그러면 131개가 다 가려면 앱을 여러 번 열어야 한다. (b)는 확인 지점이 **정확히 한 번**이고 그 뒤는 전량 |

> ### ⛔ 한도의 실제 값 — **회수는 「맥에서 지우면 끝」이 아니다**
> 업로더는 대상을 **매번 차집합으로 새로 계산한다**(「로컬에 있는데 iCloud에 없는 것」).
> 그래서 **맥에서 지우면 다음 실행이 다시 올린다.** 잘못된 자리를 치우려면
> **코드를 고쳐 새 빌드를 깐 뒤에** 지워야 한다 — 지우는 것만으로는 안 끝난다.
> **한도가 있으면 그 왕복에 131개가 안 걸린다. 이것이 한도의 실제 값이다.**
> ⚠️ 나중에 「그냥 지우면 되지」라고 읽지 않게 여기 남긴다(2026-08-19).

### 업로드 로그는 **실패만** (2026-08-19 사용자 결정)

성공 131줄을 남기면 §2-A의 「두 줄이면 정상」이 무너지고, **성공은 iCloud 폴더의 파일 자체가 증거**라
줄이 중복이다. **정상이면 0줄** — §2-A의 원칙 그대로. **진행 상황은 배너가 말한다**(§8).

### ⏸ 미결 — 한도로 멈춘 것을 화면이 어떻게 말하나 (단계 4에서 정한다)

한도로 멈추면 배너가 **「자료 옮기는 중 · 5/131」에서 사라진다** — 사용자 눈에는 멈춘 것으로 보인다.
(b)라 **첫 실행 한 번뿐**이지만 **그 한 번이 처음 켜는 순간이라 인상이 남는 자리다.**
**「5개 올렸고 나머지는 다음에」를 알릴지 단계 4에서 함께 정한다**(사용자 지시 2026-08-19).
⚠️ 화면 문구이므로 **사용자가 고른다.**

### 로컬 사본은 남긴다 (확정 — 2026-08-19)

**「잠정」을 뗐다.** 근거는 실측이다:

- **폰의 자료 전부가 32.3MB다.** 폰은 256GB 중 99GB를 쓰고 있다. **아낄 이유가 없다.**
- **로컬이 「바이트가 보장된 층」이다** — iCloud가 evict돼도 폰은 즉시 재생한다.
- 그래서 **폰에서는 §6의 「받는 중」이 사실상 안 나온다**(항상 「여기 있다」).
  **그 상태를 실제로 만나는 것은 Mac이고, 검증도 거기서 한다.**

## 6. 실체가 안 내려온 파일 — 같은 API, 다른 시점

`startDownloadingUbiquitousItem`은 이미 텍스트에서 쓰이고 있다(`FragmentFolder.read()`).
**자료도 같은 API를 쓴다. 다만 시점이 다르다.**

| | 텍스트 (지금) | 자료 (새로) |
|---|---|---|
| 무엇을 | `inbox*.md` **전부** | 그 항목 것 **하나만** |
| 언제 | **앱 시작할 때** | **상세를 열 때** |
| 왜 다른가 | 5개 · 79KB — 다 받아도 싸다 | 131개 — 다 받으면 「실체는 클라우드」가 무너진다 |

**목록·아이콘은 안 건드린다.** 필드 유무로만 그린다(`DetailView.swift:340·341·432·433`) —
**파일에 손을 안 대므로 스크롤이 다운로드를 유발하지 않는다.**

**열 때:** 상세를 열면 그 항목 자료만 받기 시작 → 받는 동안 「원본 음성 받는 중…」 →
받으면 재생 버튼·사진으로 바뀐다.

### 구현됨 (2026-08-19 · 단계 4)

`MediaFetch`(App) — 상세가 열리면 세 갈래를 재고, 「아직 안 받았다」면 받기 시작하고 기다린다.
`DetailView`의 음성·사진 줄이 세 갈래로 갈렸다. **문구는 Core(`MediaMigrationText`)에서 온다** —
사용자가 고른 말이라 화면 코드에서 짓지 않는다(시험이 문구를 못박는다).

> ### ⏸ 미결 — **「얼마나 기다리면 안 온 것인가」를 안 쟀다**
> 지금 **15초**로 두고 그 뒤에 「아직 못 받았어요 · 다시 시도」를 보인다. **이건 잰 값이 아니다** —
> iCloud 다운로드 시간은 파일 크기·회선에 달렸고 이 기기 조합에서 **측정한 적이 없다.**
> **실측 뒤 조정한다**(2026-08-19). 값은 `MediaFetch.waitSeconds` 한 곳에만 있다.

### 왜 갈라야 하나 — 이 저장소가 이미 세운 원칙

> `FolderLink.swift` 머리주석:
> *"**연결이 끊긴 것과 비어 있는 것을 절대 같게 보이지 않는다.**
> 이 판정이 없던 동안 조용히 비는 길이 다섯인데 화면에선 전부 「새 기억이 없어요」였다.
> 폴더 연결이 끊기면 사용자 눈에는 기억 전체가 사라진 것이고, 파일은 iCloud에 그대로 있는데
> 사람은 그것을 알 방법이 없어 그 순간 앱을 지웠다 깔 수도 있다."*

**자료도 똑같은 모양이다.** 「없다」와 「아직 안 받았다」를 한 문구로 뭉치면 같은 일이 일어난다.
**새 원칙이 아니라 있는 원칙의 적용이다.**

## 7. Mac에서 사진 보기 — 이번 범위에 넣는다 (2026-08-19 결정)

### 지금 상태 (조사로 확인)

### 넣는 근거 넷

1. **결정의 이유가 그것이다** — *"자료의 종류·수가 늘고 수정·삭제가 되므로 Mac에서도 쓸 수 있어야 한다."*

2. **더 나쁜 건 거짓말이다.** 파일이 Mac에 **실제로 도착해 있는데** 「이 기기엔 없음」이라고 말한다.
   iOS의 미다운로드와 달리 **영구히 틀린다.** §6의 `FolderLink` 원칙이 문제 삼는 것과 같은 종류다.
3. **★ (1)의 확정 근거가 된다** ← **사용자가 결정적이라고 한 것.**
   자료가 Mac에 도착한 것을 눈으로 봐야 하는데, 사진이 안 보이면 **음성만으로 반쪽 판정**이 된다.
4. **비용이 작다** — `photoRow`의 `#if os(iOS)`를 이미지 로딩 갈래로 바꾸는 것 +
   지도의 「지도 앱에서 열기」 한 줄(`UIApplication` → macOS 대응).

### 받아들인 대가

⚠️ **macOS 앱은 한 번도 실기기 검증된 적이 없다**(빌드만 확인). 사진을 켜면 **macOS 앱이 검증 대상이 된다.**
**사용자가 받아들였다**(2026-08-19). (1)의 목적 자체가 Mac에서 보는 것이라 어차피 생길 비용이다.

## 8. 화면 문구 (2026-08-19 사용자가 고름 — 임의 변경 금지)

| 자리 | 문구 |
|---|---|
| **이관 진행** | **「자료 옮기는 중 · 12/131」** |
| **이관 진행이 보이는 곳** | **목록 위 배너** (끝나면 사라진다) |
| **받는 중** | **「원본 음성 받는 중…」 / 「원본 사진 받는 중…」** |
| **받기 실패** | **「아직 못 받았어요 · 다시 시도」** |
| **첫 실행 한도에서 멈췄을 때** | **「자료 5개를 옮겼어요 · 나머지는 다음에」** (2026-08-19 결정) |
| ↳ 그 배너가 머무는 시간 | **3초 뒤 사라진다** — 아래 |

**받기 실패에 원인을 짚지 않는 이유:** `FolderLink`의 `unreachable` 주석과 같다 —
*"오류 코드와 원인의 대응이 문서로 보장되지 않아 **추측을 문장으로 만들면 틀린 안내**가 된다."*

### 한도 완료 문구를 이렇게 정한 이유 (2026-08-19 사용자)

**왜 이 말인가:** 「5/131」은 진행 배너와 **같은 꼴이라 멈춘 것인지 도는 것인지 안 갈린다.**
아무 말 없이 사라지면 **첫 실행에 무슨 일이 있었는지 모른다.**
이 문구는 **끝났다는 것과 아직 남았다는 것을 둘 다** 말한다.

**왜 「다음 실행까지 남긴다」가 아닌가:** 그러면 실제 수명이 **「다음 포그라운드 복귀까지」**가 되어
**5초 뒤일 수도 하루 뒤일 수도 있다**(복귀하면 한도가 풀려 나머지로 넘어가며 배너가 바뀐다).
**수명이 예측 안 되는 상태 표시는 좋지 않다.** 몇 초면 수명이 정해져 있고 **「읽으라고 띄운 것」**이라는
성격도 분명하다. 어차피 **한 번만 보이는 배너**라 오래 남길 값이 없다.

**왜 3초인가:** 저장소의 기존 자동 소멸 토스트는 **1.5초**(`RootView.swift`)이고 문구 길이도 비슷하다.
다만 그쪽은 사용자가 **직접 누른 직후** 떠서 이미 보고 있고, 이 배너는 **앱을 켜는 중**에 떠서
딴 데 보고 있을 수 있으며 **한 번만 보이므로 놓치면 다시 안 온다** → 두 배로 잡았다.

### ★ 배너는 확정 근거가 아니다 (역할을 가른다 — 2026-08-19)

| | 무엇으로 |
|---|---|
| **설치 확정 근거** | **맥의 파일** — `audio/`·`photo/` 폴더 + `.sb-media.log` + 파일 5개. **사라지지 않는다** |
| **배너** | 사용자에게 **무슨 일이 일어나는지 알리기** |

**왜 배너로 확정하지 않나:** 포그라운드 복귀만 해도 업로더가 다시 돌고 **한도가 풀려 나머지로 넘어간다** —
그 순간 완료 배너는 사라진다. 게다가 첫 실행은 **로컬 파일 5개 복사**뿐이라(평균 253KB · 계산)
**배너가 눈에 스칠 가능성이 높다 — 다만 로컬 복사 속도는 안 쟀다(추정).**

## 9. ⛔ 이 설계가 받아들인 대가 — 나중에 놀라지 않게

> ### **삭제 상태 36개(음성 28 · 사진 8)도 iCloud에 올라간다.**
> **나중에 완전 삭제를 만들 때 이것들을 회수해야 한다 — 2026-08-19에 알고 받아들인 대가다.**

**왜 그렇게 정했나:** 이번 목적이 **분실 대비**다. 폰을 잃었을 때 「삭제했던 것은 못 살린다」가 되면
**되돌릴 기회가 영영 사라진다.** 「보관함에 있는 동안은 자료도 남긴다」(자료 삭제 결정 2)와도 일관된다.

**왜 저절로 그렇게 되나:** §3의 업로더가 **op 로그를 안 보고 폴더에 있는 파일 전부**를 대상으로 삼는다.
삭제 상태를 가려내는 코드가 **없다**(넣지 않는다 — 위 결정 때문에).

**회수가 왜 어려운가 (그래서 미뤘다):** op 로그가 append-only이고 「지운다」 verb가 없다.
반쪽 삭제(create 블록만 지우고 op을 남김)는 **`raw` 없는 유령 항목**을 만든다 —
`MergeEngine.merge`는 이벤트를 id로만 묶고 **create 블록이 있는지 확인하지 않는다.**
그리고 **다른 기기가 옛 사본을 들고 있으면 되살아난다.** → 병합 설계를 건드리는 일이라 별도 과제다.
