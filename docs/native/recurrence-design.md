## 0. 한 줄

반복은 **새 분류**다(기존 6종 + 주차 위치와 나란한 하나). **며칠을 반복해도 하나의 기억**이고, 놓쳐도 항목이 늘지 않는다.

## 1. 반복은 새 분류다

기존 6종(약속·일정·할 일·정보·아이디어·원칙) + 주차 위치와 **나란한 하나의 분류**로 둔다.

- **이전 결정(O3/D3 "반복 = 속성")을 정정한다.** 근거(사용자 판단):
  1. **할 일에 반복을 섞으면 할 일 분류가 복잡해진다.** 반복을 여러 분류에 붙는 속성으로 두면 각 분류가 반복 기계를 떠안는다.
  2. **반복하는 것은 나중에 붙이는 속성이 아니라 처음부터 반복으로 시작한다.** "매일 약"·"매주 습관"은 애초에 반복으로 태어난다.
- **여기 들어가는 것:** 매일 약, 하루 3회 약, 매주 습관, 생일, 기일.

## 2. 며칠을 반복해도 **하나의 기억**이다 ★ (중심 원칙)

- 놓쳐도 **항목이 늘지 않는다.** 한 항목에 **"N일 놓침"**이 표시될 뿐이다.
- **이것이 이 설계의 중심 원칙.** 어기면 할 일 앱이 된다(놓친 회차가 항목으로 쌓이는 순간 to-do가 된다).

## 3. 반복 분류가 쓰는 세부정보 (§7 (a) "쓸지/안 쓸지" 관점)

- **반복 주기** — 매일 / 하루 N회 / 매주 요일 / 매년 이날 등.
- **자동 완성** — 세 값: **없음 / 당일 정오 / 당일 지나면**.
- **마지막 완료 시점** — 날짜가 아니라 **시점**이다(하루 여러 회차를 구분하려면 시·분이 필요, §6).
- **꺼두기** — 기간 없이 **on/off**. (잠시 멈춤용 — §5의 "그만두기(삭제)"와 구분.)
- **기준 날짜 = 기존 날짜 칸을 쓴다.** 새 칸을 만들지 않는다. **미리 알림도 그대로**(예: 생일 한 달 전 = 미리 알림).

## 4. 쌓임은 별도 규칙이 아니다

- **자동 완성 = 없음**이면 완료 말고 사라지는 길이 없어서 **쌓인다**(약).
- **자동 완성이 있으면 안 쌓인다**(습관·생일·기일 — 당일 정오/지나면 저절로 이번 회차가 닫힌다).
- **2일 놓치면 주의 표시.**

즉 "쌓임/안 쌓임"은 반복이 따로 정하는 규칙이 아니라 **자동 완성 값의 귀결**이다.

## 5. 완료의 의미가 기존과 다르다

- **기존 완료** = 한 번 하면 **영구히 끝, 단방향**.
- **반복 완료** = **"이번 회차 했다".** 마지막 완료 **시점만 갱신**되고 기억은 **살아 있다**(다음 회차로 이어진다).
- **그만두기 = 삭제.** **잠시 멈춤 = 꺼두기**(§3).
- ⚠️ **구현에서 가장 손이 많이 가는 지점.** "완료 = 영구 종료(단방향)"를 전제한 기존 완료 경로와, "완료 = 이번 회차"인 반복 완료가 **다른 의미의 같은 단어**라서 — 완료 처리·표시·병합·알림 재계산이 전부 분기된다.

## 6. 시각(시·분)이 필요하다

- **지금 앱에는 시각 개념이 없다** — 날짜만 저장되고 알림은 **오전 9시 고정**.
- 필수인 이유: **하루 3회 약**(아침 8시·점심 12시·저녁 7시), **새벽 3시 습관 알림**. **완료도 시점으로 기록**해야 회차가 구분된다(§3 "마지막 완료 시점").
- **일정의 시작·끝 시간(O1)과 같은 기반**이다 — 여기서 시각을 만들면 그쪽도 풀린다. → **O1과 상호 포인터**(`classification-redesign-open-questions.md` O1).

### 6-A. 도입 방식 조사 결론 (2026-08-02, 코드 조사 후)

**방식 (a) 확정 — 기존 날짜 칸의 값 형식을 확장한다** (`"2026-08-02"` → `"2026-08-02 08:00"`). 별도 시각 칸(b)은 쓰지 않는다.
근거 3가지:
1. **이미 문서에 그렇게 기록돼 있다** — memory-philosophy §7-2·O1: "시각 도입은 칸 추가가 아니라 **날짜 칸의 표현을 바꾸는 일**."
2. **(b)는 날짜와 시각이 각각 필드별 LWW로 병합돼 짝이 어긋날 수 있다** — A기기의 날짜 편집 + B기기의 시각 편집이 병합되면 엉뚱한 날짜+시각. (a)는 한 값이라 이 문제가 없다.
3. **(a)는 고칠 지점이 하나로 몰려 있다** — 아래 진앙.

**진앙 = `ItemSchedule.parseDay` 하나** (`ItemSchedule.swift:68-72`). due/resurface는 전 계층에서 **불투명 문자열**로 흐르다가 오직 이 함수에서만 실제 날짜로 해석된다(저장·파싱·병합은 값을 문자열로만 다룸 — 형식 무관). **옛 형식·새 형식을 모두 받게 하는 것이 전체 안전의 열쇠.**
- ⚠️ **실패 양상 = 유실이 아니라 "조용한 강등".** 지금 `split("-")` 3분할이라 시각 붙은 값은 `parseDay`가 **nil을 반환**한다 → 값은 파일에 그대로 남지만 게시·D-day·알림·규칙1 판정에서만 빠진다. **에러가 안 나므로 눈에 안 띈다 → 반드시 테스트로 잡아야 한다**(옛 값이 여전히 정상 동작함을 고정).

**직렬화는 이미 막혀 있다.** 지난주 왕복 검증(`EventWriter.isPlaintextSafe`, `EventWriter.swift:52-58`)이 **공백 값을 평문 `set`에서 거부하고 `edit fields.v1: {JSON}` 블록으로 자동 라우팅**한다 — JSON은 공백 값을 손실 없이 왕복시키므로 평문 `set` 파서의 공백-분할 잘림 위험(`EventLog.swift:112`)을 **앱 쓰기 경로에선 이미 회피**한다. **남는 구멍은 손편집·외부 도구가 평문 `set`으로 시각 값을 쓰는 경우뿐.**

**D-day 표시** — **날짜 단위 유지**(마감=기한, D±N의 유일 기준). 하루 안의 촉박함은 **보조 표시**로: 오늘/지남 항목에만 "19:00 · 3시간 남음" 같은 시각 캡션(D-숫자에 시간을 접지 않는다). 근거: `DDayCalc`가 `startOfDay` 일 경계 계산(`DDay.swift:25-27`)이라 이 방향이 코드와도 정합.

**알림** — **planner만 고치면 scheduler까지 자동 전파.** 9시 하드코딩은 Core `NotificationPlanner`의 기본 인자 한 곳뿐(`NotificationPlanner.swift:18,23-24`)이고, iOS 예약은 이미 fireDate의 시·분을 그대로 읽는다(`NotificationScheduler.swift:36-37`, `UNCalendarNotificationTrigger`). **시각 없는 항목은 9시 폴백**(기존 동작 보존). (반복은 `repeats:false`·항목당 1건·상한 32을 반복 트리거로 갈아타야 함 — §9.)

## 7. 음력

- **음력으로 저장하고 양력은 계산한다. 양력 값을 저장하지 않는다.**
  (매년 달라지므로 양력을 저장하면 이듬해 틀린 값이 남는다.)
- 계산된 양력은 **다음 회차를 정할 때만** 날짜 칸에 넣고, 회차가 지나면 **다시 계산**한다.
- **윤달:** 처음 지정한 대로(윤달로 지정했으면 윤달, 평달이면 평달). **지정한 윤달이 없는 해는 평달로** 지낸다.
- **음력 30일이 없는 달은 그 달 마지막 날로.**
- ⚠️ **미확인으로 남긴다:** 한국 음력과 iOS가 제공하는 음력 계산이 **드물게 하루 차이**가 날 수 있다. **실제 날짜(사용자 생일·기일)로 대조 검증**이 필요하다.

## 7-A. 타임존 — 벽시계로 해석, 저장하지 않는다 (2026-08-02)

**결정:** **시각은 벽시계(로컬)로 해석한다. 타임존은 저장하지 않는다.** 지금 코드가 전부 로컬(`.current`) 암묵 가정이고 타임존을 저장하지 않는 것과 정합(조사 확인 — 명시적 `TimeZone`/UTC 고정이 한 곳도 없다).

시각이 생기면 "아침 8시"가 두 뜻으로 갈린다:
- **(1) 어디에 있든 그 지역 아침 8시** (약·습관) — **지금 구조가 지원하는 것. 만들려는 것 대부분이 이것.**
- **(2) 특정 지역 기준 시각** (다른 나라와의 회의) — 지금 구조로는 안 됨.

→ **당장은 (1)만 필요하므로 문제없다.** 이 선택을 명시적으로 박아 둔다.

⚠️ **미결 (음력 미확인과 같은 성격 — 실사용/실기기로 확인):**
- **다른 타임존 기기 간 병합** — zone 없는 벽시계 값을 각 기기가 자기 로컬로 해석해 어긋날 수 있다(같은 `inbox*.md`를 서로 다른 지역에서).
- **DST 전환일** — 로컬 자정 + 고정 시각 방식(`NotificationPlanner.swift:23-25`)이 봄 DST 불연속에서 밀릴 수 있다(한국은 현재 DST 미시행이라 즉각 문제는 아님).
- **(2)가 필요해질 경우** — 그때 타임존 저장 여부를 다시 정한다.

## 이번에 하지 않기로 한 것 (미결로 기록)

- **총 완료 횟수** — 이번에 넣지 않는다. 완료할 때마다 1씩 올리는 방식은 **필드별 LWW**라 두 기기에서 각각 올리면 한 번이 사라진다(5→6, 5→6 → 병합 결과 6). 정확히 세려면 **완료 이력이나 놓친 이력**을 남겨야 하는데 그건 별건. **몇 주 써보고 필요하면 그때** 정한다.
- **세기(카운트다운·며칠째)** — D-200→D-100→D-7, 만난 지 100일·1000일, 매년 100일째 등. 이건 반복이 아니라 **한 날짜에 미리 알림이 여러 개** 붙는 것이다. §7의 **"개수는 분류가 정한다, 무제한이 기본"**에 해당하는 별도 과제. **반복과 섞지 않는다.**
- **일정의 시작·끝 시간(O1)과의 관계** — 반복 분류도 나중에 그 칸들을 쓰게 할지는 **그때 정한다.**
