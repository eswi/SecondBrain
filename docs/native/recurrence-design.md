## 0. 한 줄

반복은 **새 분류**다(기존 6종 + 주차 위치와 나란한 하나). **며칠을 반복해도 하나의 기억**이고, 놓쳐도 항목이 늘지 않는다.

## 1. 반복은 새 분류다

기존 6종(약속·일정·할 일·정보·아이디어·원칙) + 주차 위치와 **나란한 하나의 분류**로 둔다.

- **이전 결정(O3/D3 "반복 = 속성")을 정정한다.** 근거(사용자 판단):
  1. **할 일에 반복을 섞으면 할 일 분류가 복잡해진다.** 반복을 여러 분류에 붙는 속성으로 두면 각 분류가 반복 기계를 떠안는다.
  2. **반복하는 것은 나중에 붙이는 속성이 아니라 처음부터 반복으로 시작한다.** "매일 약"·"매주 습관"은 애초에 반복으로 태어난다.
- **여기 들어가는 것:** 매일 약, 하루 3회 약, 매주 습관, 생일, 기일.
- **처음엔 수동 지정만 (조사 반영 2026-08-02).** 반복은 자동분류 대상으로 넣지 않는다 — **주차와 동일**. `InboxModel.validTypes`(`:351`)·§3 프롬프트(`ClassifyPrompt.swift`·`classify.py`)를 **안 건드린다.** AI가 "recurrence"를 못 찍어도(미분류로 남음) 안전. 나중에 필요하면 편입(§2-A O4 정합).

## 2. 며칠을 반복해도 **하나의 기억**이다 ★ (중심 원칙)

- 놓쳐도 **항목이 늘지 않는다.** 한 항목에 **"N일 놓침"**이 표시될 뿐이다.
- **이것이 이 설계의 중심 원칙.** 어기면 할 일 앱이 된다(놓친 회차가 항목으로 쌓이는 순간 to-do가 된다).

## 3. 반복 분류가 쓰는 세부정보 (§7 (a) "쓸지/안 쓸지" 관점)

- **반복 주기** — 매일 / 하루 N회 / 매주 요일 / 매년 이날 등.
- **자동 완성** — 세 값: **없음 / 당일 정오 / 당일 지나면**.
- **마지막 완료 시점** — 날짜가 아니라 **시점**이다(하루 여러 회차를 구분하려면 시·분이 필요, §6).
- **꺼두기** — 기간 없이 **on/off**. (잠시 멈춤용 — §5의 "그만두기(삭제)"와 구분.)
- **기준 날짜 = 기존 날짜 칸을 쓴다.** 새 칸을 만들지 않는다. **미리 알림도 그대로**(예: 생일 한 달 전 = 미리 알림).
- **저장(조사 반영 2026-08-02) = 새 필드로.** 반복 주기·자동 완성·마지막 완료 시점·꺼두기는 **기존 칸(due/resurface/status) 재사용이 아니라 새 필드**다. `MergeEngine`이 필드별 LWW라 **새 필드를 코드 추가 없이 자동 병합**한다(조사 확인). due/resurface는 **현재 회차 날짜**를 들고 있어야 해 재사용 불가, status는 위 §5 이유로 불가. (기준 날짜만 기존 칸을 쓰고, 반복 설정·완료 시점은 새 필드.)

### 3-A. 두 날짜 칸의 역할 (2026-08-03 정정 ★ — 앵커를 마감으로)

> **정정(2026-08-03):** 처음엔 "미리 알림 = 앵커, 마감 안 씀"으로 잡았으나, **lead-time을 담을 칸이 없어서**(8시 약을 7시부터 알리기) **뒤집었다.** 앵커 = 마감. 두 칸 역할이 일반 항목과 완전히 같아진다.

**되풀이도 일반 항목과 동일하게** — 마감 = 기한/회차, 미리 알림 = 게시 시작:

- **마감(due) = 회차 앵커 = 회차 시각(8시).** **완료·catch-up이 이 값을 다음 회차로 전진**시키고, **놓침·D-day 배지가 이 칸 기준.** ClassSpec: 되풀이 `uses = mirror`(마감 씀). 라벨 = 되풀이 마감 "**회차 시각**".
- **미리 알림(resurface) = 게시 시작(lead, 7시).** 게시 게이트(시각 인지)가 이 값을 보고 언제부터 '지금 챙길 것'에 띄울지 정한다. **완료 시 마감과 같은 간격만큼 함께 전진해 lead(예: 1시간)를 보존.**
- **마감만 있고 미리 알림 없어도 된다** — 되풀이는 **마감 분기도 시각 인지**라 **마감 시각부터 보인다**(lead 0). 즉 lead는 선택.
- **회차 시각(마감)이 없으면 회차가 안 돈다.** → 조용히 안 도는 것을 막는다: 미리 알림/마감 둘 다 "시간 설정"에 보이고(일반 항목과 동일), **마감이 비면 상세 상단 "회차 시각이 없어요" 안내 배너**(#3 (c)).
- **규칙 1(§ItemSchedule) = 같은 규칙, 시각 유무로 적용만 다름:** 미리 알림은 마감보다 실제로 앞서야 한다 — **date-only면 최소 하루 전, 시각 있으면 `미리 알림 ≤ 마감`**(이후만 위반, 정각 허용). 목적(항목이 자기 마감 지날 때까지 숨는 것 방지)은 그대로.
- **데이터 정합(옛 데이터):** 마감에 시각을 넣은 옛 되풀이는 **이 모델과 그대로 맞다**(마감=앵커). 미리 알림(lead)은 원하면 추가.

⚠️ **Stage 5로 넘길 것 — lead-time 알림 구멍.** 지금 알림은 `publishDay`(미리 알림 우선) **한 지점**에서만 발화(`NotificationPlanner`). 그래서 **7시 미리 알림 + 8시 마감 약은 7시에만 울리고 정작 8시(회차)엔 안 울린다.** 하루 단위일 땐 덜 중요했지만 한 시간 전이면 다르다. **Stage 5(알림 전환)에서 미리 알림·마감 둘 다(또는 회차 시각에) 울리도록 다룬다. 지금 안 고침.**

## 4. 쌓임은 별도 규칙이 아니다

- **자동 완성 = 없음**이면 완료 말고 사라지는 길이 없어서 **쌓인다**(약).
- **자동 완성이 있으면 안 쌓인다**(습관·생일·기일 — 당일 정오/지나면 저절로 이번 회차가 닫힌다).
- **2일 놓치면 주의 표시.**

즉 "쌓임/안 쌓임"은 반복이 따로 정하는 규칙이 아니라 **자동 완성 값의 귀결**이다.

**⚠️ 자동 완성은 앱이 켜져야 판단된다 (조사 반영 2026-08-02).** 백그라운드 데몬이 없어(`resolve()`는 상태를 바꾸는 로직이 없다 — 순수 파일→병합→목록), "당일 정오"·"당일 지나면"은 **앱 열 때 catch-up으로 지연 계산**된다. **앱을 며칠 안 열면 그동안 자동 완성이 안 일어나고, 다음에 열 때 일괄 처리**된다. 특히 **"당일 정오" 자동 완성은 그날 앱을 안 열면 다음 실행(앱 열기)까지 남아 있다** — 이 한계를 안고 간다.
- ↔ **알림은 iOS가 직접 발화하므로 앱과 무관**하게 제 시각에 온다(§9 반복 트리거). **알림(iOS가 함) vs 자동 완성·놓침 계산(앱 열 때만 함)** 이 둘은 갈린다.

## 5. 완료의 의미가 기존과 다르다

> ### ⚠️ 이름 규칙 — 이 문서엔 **"5-"로 시작하는 계열이 둘** 있었다 (2026-08-05 정리)
>
> §5(완료의 뜻)의 하위 절과 §9(알림)의 **Stage** 단계가 **둘 다 `5-A`·`5-B`·`5-C`** 를 썼다.
> 한때 이 파일에 **`### 5-A` 제목이 두 개**였다(§5의 것 / §9의 "5-A 정정 경위"=알림 쪽).
> **겹치는 이름은 문서에 주의를 적어두는 것으로 안 풀린다** — 전례: 결정 **D3**(반복=속성)와 **Stage D3**가
> 겹쳐 있었고 문서에 적혀 있었는데도 "D3 완료"로 잘못 전달돼 왕복이 생겼다. 그래서 **이름 자체를 갈랐다.**
>
> | 계열 | 표기 | 내용 |
> |---|---|---|
> | **§5 하위** | **낱말** — `§5-대가` · `§5-조사` · `§5-증인` | 완료의 뜻·판정 |
> | **§9 하위** | **`Stage` 접두 필수** — `Stage 5-0`·`5-A`~`5-E` | 알림 전환 단계 |
>
> **옛 이름 대응(과거 worklog·커밋 메시지가 이 이름으로 적혀 있다):**
> `§5-A` → **`§5-대가`** / `§5-B` → **`§5-조사`** / `§5-C` → **`§5-증인`**.
> **Stage 쪽은 안 바꿨다** — 진행 중인 단계(5-C·5-D·5-E)라 참조가 많고 `Stage` 접두로 이미 구분된다.
> 앞으로 **§9 계열은 맨몸 `5-C`로 쓰지 말고 반드시 `Stage 5-C`** 로 쓴다(이번에 전부 고쳤다).

- **기존 완료** = 한 번 하면 **영구히 끝, 단방향**.
- **반복 완료** = **"이번 회차 했다".** 마지막 완료 **시점만 갱신**되고 기억은 **살아 있다**(다음 회차로 이어진다).
- **그만두기 = 삭제.** **잠시 멈춤 = 꺼두기**(§3).
- ⚠️ **구현에서 가장 손이 많이 가는 지점.** "완료 = 영구 종료(단방향)"를 전제한 기존 완료 경로와, "완료 = 이번 회차"인 반복 완료가 **다른 의미의 같은 단어**라서 — 완료 처리·표시·병합·알림 재계산이 전부 분기된다.

**조사 반영 (2026-08-02) — 이 지점의 실체:**
- 지금 완료는 `markDone()` → `set status=done`(`InboxModel.swift:222`)이고, **done 항목은 `liveNonDone`(`InboxModel.swift:196`)에서 빠져 보관함으로 간다** — 살아있는 목록·알림 전부에서 제외.
- 그래서 **반복 완료에 `status=done`을 그대로 쓰면 매 회차마다 항목이 보관함으로 사라진다 = 중심 원칙(§2 "하나의 기억") 붕괴.** 이것이 "완료 버튼이 분류로 분기해야 한다"의 실체다.
- **반복 완료 = status를 안 건드리고 새 필드(마지막 완료 시점)에만 기록** → 항목은 살아있고 다음 회차로 이어진다. 완료 버튼(`InboxView.swift:154·159·171`, `LivingView.swift:50·57`)이 type으로 분기.
- 참고: `status`는 per-field LWW라 **done도 되돌릴 수 있다**(`restore()`=`set status=open`, `InboxModel.swift:399`). 단방향 grow-only인 `confirmed`와는 다르다 — 반복 완료엔 status 계열이 맞다.

**완료가 남기는 것 = 두 값 (2026-08-05 저녁 확정, §5-증인):**
- **`lastDone`** — 완료한 **시점**(벽시계, 시각 표준형 T). 놓침·취소가 쓴다.
- **`lastDoneDue`** — 그 완료가 회차를 옮긴 **목적지**(= 완료가 만든 `due` 값, `due`와 같은 형식).
  **"이번 회차를 완료로 닫았나"의 유일한 증인**이다. 자동완성(catch-up)은 마감을 옮기되 **이 필드를 안 쓴다** —
  그래서 "했다"와 "넘어갔다"가 **판정으로** 갈린다(문장이 아니라 구조로).
- 판정: **`lastDoneDue == due` 이고 `due > now` 이고 회차가 아직 안 열렸으면(`!isPublished`) "이번 회차 완료"**.
  화면 동작 세부는 §5-증인.

### 5-대가. 이른 완료 under-claim의 대가 — (a) 고쳤고 (b) 남는다 (2026-08-05)  *(옛 이름 §5-A)*

> **⚠️ 정정 (2026-08-05 저녁) — 이 절의 제목과 결론이 둘 다 틀렸다. 아래 옛 서술은 지우지 않고 남긴다.**
>
> **두 번 뒤집힌 경위:**
> 1. 08-05 낮 — (a)(재완료 데이터 유실)를 후보 ②(재완료만 멱등)로 고쳤다고 적었다. → 이 절.
> 2. 08-05 저녁 — (b) 방향을 정하고 착수 전 계측하다가 **그 "고쳤다"가 반쪽이었음**을 발견했다.
>
> **틀린 것 ①: "(a) 고쳤다 / 데이터 유실은 이미 없다".** 가드(`alreadyClosedThisCycle`)의 2절이
> `now ≤ 방금 닫은 회차`를 요구해서 **회차 시각을 지나면 풀렸다.** 계측(이른 완료 08-05 07:30, 마감 08-06):
> `07:35 막힘 ✓ / 08:01·09:00·23:00 통과 → 마감 08-07` — 즉 막은 것은 **회차 시각 이전의 재압뿐**이고,
> **8시가 지나면 내일 약이 그대로 사라진다.** 데이터 유실 경로는 열려 있었다(**구멍 1**).
> 아이러니하게도 §5-조사가 후보 ①(가드형)의 단점으로 지적한 *"시간이 지나면 다시 벌어진다"* 가
> **(a)의 가드 자체에 있었다.** → **§5-조사 마지막 줄 "(a)가 막혔으므로 데이터 유실은 이미 없다"도 함께 틀렸다.**
>
> **틀린 것 ②: 문제의 방향을 under-claim 하나로만 봤다.** 같은 계측에서 **반대 방향**이 나왔다 —
> 정시 완료한 항목이 **lead 창(미리 알림~마감)에서 '지금 챙길 것'에 있으면서 "완료" 칩**을 달고 있었다
> (= 안 먹은 약을 먹었다고 함, **구멍 2**). **under-claim은 사람이 다시 누르면 되지만 거짓 완료는
> 약을 안 먹고 넘어가게 만든다** — 우선순위가 더 높다.
>
> **둘 다 §5-증인에서 닫혔다.** 이 절이 "피드백은 지금 만들지 않는다 — (b)와 같은 뿌리라 따로 고치면 두 번
> 손대게 된다"고 적은 판단 자체는 맞았다. 틀린 것은 **(a)가 이미 닫혔다고 본 것**이다.

이른 완료(마감 시각 **전에** 완료)는 `doneThisCycle`이 **false**로 판정한다 — `lastDone ≥ 직전 회차`를 요구하는데 마감 전에 눌렀으니 미달이다. 자동 전진을 "완료"라 부르지 않으려는 **의도된 under-claim**이지만(D-3), 그 대가로 화면에서 **완료 표시가 안 뜨고 `[이번 것 했어요]`가 돌아온다.** 여기서 둘이 갈라졌다:

- **(a) 다시 누르면 회차가 또 전진한다 → ~~고쳤다~~ 절반만 막았다(2026-08-05 낮 → 저녁 정정).** `completionChanges`가 이미 닫은 회차에 **빈 변경**을 돌려준다(`alreadyClosedThisCycle`). **새 필드 없이** `stepBack(due)`로 판정하므로 저장할 게 없다 — 병합 어긋남·마이그레이션·취소 로직 수정이 전부 없다. 고치기 전 동작: 마감 08-05 → 1차 08-06 → **2차 08-07**(하루 건너뜀 = 내일 약이 목록·알림에서 사라짐, 이 설계의 출발점인 바로 그 경우).
  **⚠️ 이 "고쳤다"가 틀렸다(위 정정 블록).** 2절의 `now ≤ 방금 닫은 회차` 조건 때문에 **회차 시각을 지나면 가드가 풀려** 같은 유실이 그대로 났다. "새 필드 없이"가 이 절의 자랑이었는데, **새 필드가 없어서 회차 시각 말고는 기댈 것이 없었던 것**이 원인이다. §5-증인에서 그 필드를 만들며 2절은 삭제됐다.
- **(b) 이른 완료를 무를 수 없다 → 남긴다.** `[취소]`가 그 상태에서 안 그려진다(완료 표시가 없으니 취소 자리도 없다).

⚠️ **(a)만 막으면 "눌러도 반응 없는 버튼"이 남는다 — 이 둘은 묶여 있다.** 원인이 하나(표시가 under-claim이라 버튼이 완료 전 상태로 보인다)여서, (a)의 가드는 **해를 없애지만 이상함을 없애지 못한다.** 정확히 말하면:

- **상세 버튼**: 눌러도 회차는 안 움직이는데 `cycleDoneLocal = true`를 낙관적으로 세우므로(`DetailView:537`) 화면은 "이번 회차 완료됨 ✓"로 바뀐다 → **닫고 다시 열면 또 `[이번 것 했어요]`.** 반응은 있으나 **거짓 반응**이다.
- **목록 스와이프 "했어요"**: 아무 반응이 없다.

즉 사람은 "눌렀는데 안 된다"로 느낀다. **피드백은 지금 만들지 않는다** — (b)(무를 수 없음)와 **같은 뿌리**라 따로 고치면 두 번 손대게 된다. 표시를 손볼 때 둘을 함께 본다. (표시를 맞추려고 `lastDone`만 갱신하는 변형은 under-claim을 부분적으로 가려 (b)의 판단을 흐리므로 **일부러 안 했다.**)

### 5-조사. (b) 방향 후보 조사 — 계측 결과 (2026-08-05, **결정 아님**)  *(옛 이름 §5-B)*

**흔들리는 곳은 게이트가 아니라 catch-up과의 구분이다.** 두 상태를 만들어 재봤다:

**후보별 결론**
- **① 완료의 정의 변경 = "회차 시각 **이후**의 완료" → "회차 **창 안**의 완료".** §5의 원칙 문장은 형식상 유지되지만(catch-up은 여전히 `lastDone`을 안 씀) **원칙이 지켜지는지는 문장이 아니라 판정이 정한다** — 소박한 ①에서는 **안 지켜진다**(B@12:30 = true). 지켜지게 하려면 `now ≤ 방금 닫은 회차`가 필수고, 그건 **완료 표시가 회차 시각에 만료된다**는 뜻이다(7시 30분에 먹고 8시에 칩이 꺼진다). under-claim(아예 안 뜸)을 **깜빡이는 claim**으로 바꾸는 셈이다.
- **③이 못 막는 것 셋.** ⑴ 표시 predicate를 안 건드리므로 **dead button 그대로**(무르기만 열린다). ⑵ `completionRow`가 if/else 한 덩어리라 false 가지에 취소를 함께 그리면 **"[이번 것 했어요]"와 "[취소]"가 동시에** 뜬다("안 했음"이라 말하며 취소를 권함). ⑶ **가장 큰 것 — `undoRecurComplete`는 완료 전용이 아니다.** `priorValue`는 "그 필드를 건드린 **두 번째 최신 이벤트**"를 되돌리는데 catch-up·resume도 `due`/`resurface` 이벤트를 쓴다(`InboxModel:218-225`) → 취소를 항상 그리면 **자동 전진을 되돌리는 버튼**이 되어 마감이 과거로 복원되고 놓침·알림이 되살아난다. 취소 후에도 `lastDone`(직전 값)이 남으면 계속 그려져 **이력을 거슬러 올라간다**(지금은 `cycleDoneLocal=false`로 사라져 못 한다).
- **"눌러도 반응 없는 버튼"은 뿌리가 predicate가 둘이라는 것이다** — 버튼은 `doneThisCycle`(표시)로 그려지고 누르면 `alreadyClosedThisCycle`(행동)이 거부한다. **③ 단독: 따로 남는다.** **①(가드형): 창 안에서만 사라지고 회차 시각을 지나면 되돌아온다**(표시만 뒤집히고 행동은 계속 거부) — 하나로 풀리는 게 아니라 **시간에 따라 다시 벌어진다.** **①(소박): 셋 다 풀리지만 witness가 깨진다.**

**조사하다 나온 세 번째 길 — 닫은 회차의 앵커를 기록한다**(예: `lastDoneCycle` = 그 회차 시각). 필드가 답을 못 하니 표시를 고치려면 답을 만들어야 한다. 넷이 한 번에 풀린다: **표시**(닫은 회차 == 지금 회차면 "완료" — 회차 내내 유지되고 catch-up은 이 필드를 안 쓰니 "넘어감"과 구분이 **판정으로** 지켜진다) · **취소**(그 필드가 이번 회차를 가리킬 때만 → ③의 구멍 셋이 닫힌다) · **dead button**(predicate가 하나가 되어 사라진다) · **(a) 가드**(`stepBack` 휴리스틱 대신 이 필드로 판정 — "하루 N회 때 재검토" 주석도 해소).
**비용 = (a)에서 일부러 피한 것들이 돌아온다:** 새 필드의 per-field LWW 병합 · 마이그레이션(옛 항목은 `doneThisCycle`로 폴백) · 취소가 이 필드도 되돌려야 함. 다만 grow-only가 아니라 **덮어쓰기 필드**라 `confirmed`보다 병합 축은 단순하다.

**→ 사양서 대화로 가져갈 질문은 "후보 셋 중 무엇"이 아니라 하나다: 표시를 고치려면 어느 회차를 닫았는지 기록해야 하는데, 그 값을 치를 것인가.** 치르지 않기로 하면 남는 선택은 **(b)를 열어둔 채 under-claim 유지**이고, 그건 지금 상태이며 ~~**(a)가 막혔으므로 데이터 유실은 이미 없다.**~~
**⚠️ 마지막 절이 틀렸다(위 정정 2).** (a) 가드는 회차 시각 뒤에 풀렸다 — **치르지 않기의 대안은 "유실이 열린 현상유지"였다.** 이걸 알았다면 이 질문은 애초에 덜 팽팽했을 것이다.

**→ 답: 치른다 (2026-08-05 저녁, 사용자 승인). 구현은 §5-증인.**

### 5-증인. (b) 치렀다 — 완료가 닫은 회차를 기록한다 (`lastDoneDue`) ✅구현됨 2026-08-05 (헤드리스)

> **실기기 미확인** — 2026-08-05 밤엔 일부러 설치하지 않았다(E-6 판정 08-06 오염 방지). 확인 절차 = `recurrence-verify-checklist.md` **F절**.

**필드 = `lastDoneDue`.** 완료가 회차를 옮긴 **목적지**(= 그 완료가 만든 `due` 값). 형식은 **`due`를 그대로 복사**(T 강제 안 함 — date-only 되풀이에 없는 시각을 만들어 붙이지 않는다). 비교는 `parseDay`로.

**§5-조사는 "닫은 회차"를 적자고 했는데 "목적지"로 바꿨다(승인됨).** 근거: **밀린 완료**(마감 08-02를 08-05에 완료 → k=4회차 전진)에서 닫은 회차를 적으면 현재 `due`와의 거리 k가 데이터에 없어 판정이 **다시 휴리스틱**이 된다 — 그리고 그 경우가 하필 **"3일 놓친 약을 오늘 먹기"**, 이 설계의 출발점이다. 목적지를 적으면 **등식 하나**로 끝나고 k와 무관하다. 병합에서도 안전하다: 두 기기의 완료·catch-up이 필드별 LWW로 엇갈리면 등식이 깨져 **under-claim(안전) 쪽으로 강등**되지 거짓 완료가 되지 않는다. 닫은 회차 자체는 이벤트 로그에 남아 잃는 정보가 없다.

**판정 하나 = 세 절.** 표시(칩·배너)·완료 버튼·취소 버튼·재완료 가드가 **전부 이것 하나**를 본다.

| 절 | 하는 일 |
|---|---|
| `due > now` | 앵커가 미래여야 이번 회차가 닫힌 것. **꺼둔 항목**이 앵커를 지나도 칩이 안 남게 하는 절이기도 하다 |
| `lastDoneDue == due` | **완료 vs 넘어감.** catch-up은 이 필드를 안 쓰므로 등식이 깨진다 |
| `!isPublished` | **다음 회차가 아직 안 열렸다.** 구멍 2를 닫는 절 — 게이트를 "공유"가 아니라 **그대로 호출** |

**옛 항목은 폴백.** `lastDoneDue`가 없으면 **옛 판정 그대로**(마이그레이션 금지 — 저장소 원칙). 항목은 다음 완료 때 필드를 얻어 저절로 새 경로로 옮겨간다.

**닫힌 것 다섯:**
- **under-claim** — 이른 완료도 "이번 회차 완료됨"으로 뜨고, **회차 시각에 안 꺼진다**(§5-조사가 ①(가드형)의 단점이라 부른 "만료"가 없다).
- **(b) 무를 수 없음** — 그 화면에 `[취소]`가 그려진다.
- **dead button 둘** — **가드 = 표시**라 상세는 구조적으로 소멸한다(판정이 false여서 버튼이 보이면, 누를 때 반드시 변경이 나온다). §5-대가가 함께 지목한 **목록 스와이프 "했어요"** 도 같은 판정을 물렸다(`cycleAlreadyDone`, 5곳).
- **구멍 1** — `stepBack` 휴리스틱 2절을 **삭제**했다. 하루 종일 멱등이다.
- **구멍 2** — 3절이 게이트를 그대로 쓴다.
- **③의 구멍 셋도 함께** — 취소는 등식이 설 때만 그려지므로 되돌리는 대상이 **언제나 완료**다(자동 전진을 되돌리는 버튼이 될 수 없다). 취소하면 마감이 과거로 가 게시되고 판정이 false가 돼 취소가 사라진다 → **이력을 거슬러 올라가지 못한다.**

**치른 대가 (승인됨) — 이른 완료 뒤 다음 회차의 이른 완료는 회차가 열려야 가능하다** (미리 알림 시각, 없으면 마감 시각).
구멍 1을 닫으면 **피할 수 없다**: "잘못된 재압"과 "다음 회차의 이른 완료"는 **필드 상태가 완전히 같고 `now`만 다르다.** 둘을 가르려면 "회차가 언제 열리나"가 필요하고, 그 값은 이미 있다 — 미리 알림. 받아들이는 근거 셋:
1. **유실이 아니라 기다림이다** — 회차가 열리면 목록에 떠서 재촉한다.
2. **"이르게 하려면 미리 알림을 걸어라"가 미리 알림 칸의 원래 뜻과 같다**(§3-A: 미리 알림 = 게시 시작).
3. **날짜 경계로 가르는 변형은 하루 N회에서 깨진다** — 회차가 같은 날 안에서 돌기 때문. §5-조사가 (b)의 이득으로 꼽은 *"하루 N회 때 재검토 주석 해소"* 가 되살아난다. 등식은 시각별 회차에도 그대로 성립한다.

**남은 것:** F절 실기기 확인. 그리고 **§5-대가가 옛 판정으로 적어 둔 서술 일부는 이제 옛 동작 기록**이다(지우지 않고 정정 블록으로 표시).

### 6-A. 도입 방식 조사 결론 (2026-08-02, 코드 조사 후)

**방식 (a) 확정 — 기존 날짜 칸의 값 형식을 확장한다** (`"2026-08-02"` → `"2026-08-02 08:00"`). 별도 시각 칸(b)은 쓰지 않는다.
근거 3가지:
1. **이미 문서에 그렇게 기록돼 있다** — memory-philosophy §7-2·O1: "시각 도입은 칸 추가가 아니라 **날짜 칸의 표현을 바꾸는 일**."
2. **(b)는 날짜와 시각이 각각 필드별 LWW로 병합돼 짝이 어긋날 수 있다** — A기기의 날짜 편집 + B기기의 시각 편집이 병합되면 엉뚱한 날짜+시각. (a)는 한 값이라 이 문제가 없다.
3. **(a)는 고칠 지점이 하나로 몰려 있다** — 아래 진앙.

**진앙 = `ItemSchedule.parseDay` 하나** (`ItemSchedule.swift:68-72`). due/resurface는 전 계층에서 **불투명 문자열**로 흐르다가 오직 이 함수에서만 실제 날짜로 해석된다(저장·파싱·병합은 값을 문자열로만 다룸 — 형식 무관). **옛 형식·새 형식을 모두 받게 하는 것이 전체 안전의 열쇠.**
- ⚠️ **실패 양상 = 유실이 아니라 "조용한 강등".** 지금 `split("-")` 3분할이라 시각 붙은 값은 `parseDay`가 **nil을 반환**한다 → 값은 파일에 그대로 남지만 게시·D-day·알림·규칙1 판정에서만 빠진다. **에러가 안 나므로 눈에 안 띈다 → 반드시 테스트로 잡아야 한다**(옛 값이 여전히 정상 동작함을 고정).

**직렬화는 이미 막혀 있다.** 지난주 왕복 검증(`EventWriter.isPlaintextSafe`, `EventWriter.swift:52-58`)이 **공백 값을 평문 `set`에서 거부하고 `edit fields.v1: {JSON}` 블록으로 자동 라우팅**한다 — JSON은 공백 값을 손실 없이 왕복시키므로 평문 `set` 파서의 공백-분할 잘림 위험(`EventLog.swift:112`)을 **앱 쓰기 경로에선 이미 회피**한다. **남는 구멍은 손편집·외부 도구가 평문 `set`으로 시각 값을 쓰는 경우뿐.**

**D-day 표시** — **날짜 단위 유지**(마감=기한, D±N의 유일 기준). 하루 안의 촉박함은 **보조 표시**로: 오늘/지남 항목에만 "19:00 · 3시간 남음" 같은 시각 캡션(D-숫자에 시간을 접지 않는다). 근거: `DDayCalc`가 `startOfDay` 일 경계 계산(`DDay.swift:25-27`)이라 이 방향이 코드와도 정합.

**알림** — **planner만 고치면 scheduler까지 자동 전파.** 9시 하드코딩은 Core `NotificationPlanner`의 기본 인자 한 곳뿐(`NotificationPlanner.swift:18,23-24`)이고, iOS 예약은 이미 fireDate의 시·분을 그대로 읽는다(`NotificationScheduler.swift:36-37`, `UNCalendarNotificationTrigger`). **시각 없는 항목은 9시 폴백**(기존 동작 보존). (반복은 `repeats:false`·항목당 1건·상한 32을 반복 트리거로 갈아타야 함 — §9.)

### 6-B. 시각 구현 단계 (승인 2026-08-02)

**원칙:** parseDay 확장은 **독립 단계**, "옛 값 정상 동작"을 테스트로 고정한 뒤에만 다음으로. 실기기 확인은 단계마다 걸지 않고 **헤드리스로 갈 수 있는 데까지 간 뒤 한 번에 몰아서.**

**쓰기 표준형 = `"YYYY-MM-DD'T'HH:mm"`** (예: `2026-08-05T19:00`). **읽기는 관대**(공백·`T`·date-only 전부 수용), **쓰기는 `T`.** 이유: 공백은 `isPlaintextSafe`의 JSON 라우팅에 기대는 방식이라 그 판단이 바뀌면 함께 무너진다; `T`는 평문 `set` 경로에서도 애초에 안 잘린다. 기존 데이터에 공백 형식이 없으니 지금 정하는 게 싸다.

**Stage 0 — 그물 먼저.** 코드 무변경. 특성화 테스트로 현행 date-only 동작을 고정(옛 값 회귀 감지선).

**Stage 1 — 엔진: `parseDay` 확장 (독립 단계) ★.**
- 바뀌는 것: `ItemSchedule.parseDay`(읽기 관대) + `timeOfDay` 보조 함수 + `NotificationPlanner`가 값의 시각을 읽어 발화(**시각 없으면 9시 폴백**). date-only는 자정 Date로 **동작 불변**(모든 게이트가 `startOfDay`). **시각 부분이 깨져도 날짜는 살린다**(유실 방지 — 값 안 지움).
- 테스트:
  - **양성(있어야 할 자리에 나타남):** 마감 `"2026-08-05 19:00"` → 오늘(08-02) **D-3** / 미리 알림 `"2026-08-02 08:00"` → **오늘 게시** / `"2026-08-03 08:00"` → **오늘 게시 안 됨**.
  - **음성(빠지지 않음):** 시각 값 항목이 D-day·게시·알림에서 **조용히 강등되지 않음**.
  - **짝 비교(핵심 그물):** `"2026-08-05"` 와 `"2026-08-05 19:00"`(및 `T`형)이 **D-day·게시·정렬·규칙1에서 동일**, **알림 발화 시각만 다름(9시 vs 19시).**
  - **옛 값 동일:** `"2026-08-05"`의 Date·판정이 지금과 동일.
  - → 헤드리스 완결. **여기서 보고·멈춤·승인 후 Stage 2.**

**Stage 2 — UI 입출력 (표시+입력 한 단계).** *(2·3 병합 — 표시만 먼저 하면 시각 있는 항목이 없어 확인할 게 없다.)* **구현됨 2026-08-02(헤드리스).**
- `DetailView`: 날짜 피커(`.date`, 시각 보존) + **"시각" 토글** + 시·분 피커(`.hourAndMinute`) → **쓰기 표준형 `T`**(`dayTimeString`). `Components` 캡션에 시각 노출(`T`→공백) + **목록 오른쪽 시각 칩**(`scheduleTimeChip`).
- **보조 시각 칩은 마감(기한) 기준만** (2026-08-02 정정, 실기기 지적) — D-day 배지와 **동일 규칙**(`deadlineDay`). 마감에 시각 있을 때만 오늘=`N시간 남음`/`지남`·다른 날=마감 `HH:mm`. **마감 없으면(미리 알림만) 칩 없음** — "며칠/몇시간 남음"은 기한이 있어야 성립(미리 알림은 게시·알림 시각이지 카운트다운 대상이 아니다). 처음엔 마감 없을 때 미리 알림 시각으로 폴백해 카운트다운을 띄운 버그가 있었음(`fc9c0da` 뒤 정정).
- 헤드리스 그물: `dayTimeString` 왕복 · `withTimeOfDay` 보존/날짜만 · 미루기 시각 보존 · `withinDayCaption`.

**Stage 2 세 결정 (2026-08-02):**
1. **시각 안 넣을 자유 = 유지.** 상세의 **"시각" 토글**(기본 OFF)로. OFF면 날짜만 저장(`YYYY-MM-DD`, `T` 없음), ON이면 기본 `T09:00`을 열어 시·분 지정. "날짜 설정" 버튼·미분류 기본값·기존 값은 전부 date-only 그대로.
2. **자정 처리.** "시각 없음"은 **date-only 문자열**(토글 OFF)로 표현하므로, `T00:00`은 **글자 그대로 자정**(토글 ON에서 명시적으로 고른 경우만). `parseDay`는 둘 다 자정 Date라 **날 단위 판정은 동일**, `timeOfDay`만 갈라 **알림이 자정 vs 9시**로 다르다. → 00:00을 "시각 없음"에 뺏기지 않고 실제 자정 알람도 가능하게 남긴다.
3. **미루기 = 원래 시각 보존.** 미루기(+7일)는 **날짜만 새로 정하고 원래 미리 알림의 시각을 유지**한다(`withTimeOfDay` — 약 아침 8시 → 미뤄도 8시). 시각 없던 값은 날짜만. 날짜 피커로 날짜를 바꿔도 같은 방식으로 시각 보존. **규칙1은 날짜 단위 유지**(Stage 1 짝 비교로 확인 — 시각 유무와 무관하게 동일).

**Stage 2 미결 (기록만):**
- **목록 캡션 폭** — 지금 챙길 것 목록 캡션에서 **수집 시각 제거**(상세 "최초 수집"에 남음) + **연도 생략**(올해면 `08-05`, 다른 해면 `2027-08-05`, 내년 마감 오해 방지)으로 미리 알림 시각까지 한 줄에 보이게 함(`itemCaption`·`displaySchedule`).
- **발견성** — 날짜 없는 줄엔 시각 토글이 안 뜬다(`timeRow`의 `if hasDate`, 맞는 동작). 새 항목에서 시각을 넣으려 하면 넣을 자리가 없는 것처럼 읽힌다. "날짜 설정 → 그다음 시각 토글" 순서를 사람이 알아야 함. 개선 후보(나중): 날짜 없을 때도 시각을 바로 열기. → `time-of-day-verify-checklist.md` 미결과 동일.

**Stage 3 — 자동분류 (나중·선택).** `ClassifyPrompt`는 date-only 유지. 시각은 반복 분류가 들어올 때. 이 조각에선 안 건드림.

**타임존:** 무변경(§7-A, 로컬 벽시계).

**실기기 확인 (마지막에 몰아서 — Stage 2까지 헤드리스 끝낸 뒤 1회 설치):**
- 상세에서 시각 입력(피커에 시·분) → 저장 → 재열람 시 시각 유지, 파일에 `...T HH:mm` 기록.
- 옛 date-only 항목도 그대로 편집됨.
- 목록·캡션에 시각 노출, 오늘/지남 항목 "N시간 남음" 보조 표시.
- 시각 있는 항목 알림이 그 시각에, 시각 없는 항목은 9시에 발화.
- → 확인 목록은 확정 시 체크리스트 파일에 남긴다(대화에만 두지 않는다 — 지난주 검증 목록이 그렇게 사라졌다).

⚠️ **미결 (음력 미확인과 같은 성격 — 실사용/실기기로 확인):**

## 10. 양력 반복 — 구현 단계 (2026-08-02, 승인 대기)

**원칙:**
- **완료 분기(Stage 3)는 독립 단계** — **유일한 파괴적 지점**(잘못하면 기억이 보관함으로 사라짐).
- **기존 완료 동작 불변을 테스트로 먼저 고정**(Stage 0)한 뒤 손댄다(시각 Stage 0과 같은 방식).
- **알림 전환(Stage 5)은 뒤로** — 화면에서 반복이 도는 걸 먼저 보고 나서.
- **실기기 확인은 몰아서 한 번에**(Stage 5 후) — 헤드리스로 갈 수 있는 데까지 간 뒤.
- **음력은 이 계획 밖**(순서표 다음 조각).

**Stage 0 — 그물 먼저 (기존 완료 고정).** 코드 무변경. 테스트로 현행 완료 못박기: `markDone`→`status=done`→항목이 `liveNonDone`에서 빠져 보관함(`doneItems`)으로 / `restore`→`status=open`→복귀 / done은 알림에서도 제외. **회귀 감지선**(Stage 3에서 기존 완료가 안 변함을 지킨다).

**Stage 1 — 분류 추가 (비파괴·수동 지정).** `ClassSpec.all`에 `recurrence` + 시각 메타(`Theme.swift` `TypeCatalog.allKnown` 또는 `ClassDef.swift` 특례 — **안 하면 회색 미분류로 렌더**). `validTypes`·프롬프트 **안 건드림**. 검증: 기존 항목 판정 불변(Q7), 새 분류가 메뉴·칩·글리프에 제 색으로 뜸, 상세 "시간 설정"에 due·resurface 나옴. 헤드리스: ClassSpec 테스트 + 빌드.

**Stage 2 — 반복 세부 필드 저장 + 입력 UI.** 새 필드(주기·자동완성·꺼두기)를 상세에서 설정·저장(필드별 LWW 자동 병합). **완료·회차는 아직 안 건드림** — 설정만 왕복. 검증: 필드 왕복·병합 헤드리스 테스트.

**Stage 3 — 완료 분기 (★ 독립·유일 파괴적).** 완료 버튼이 type 분기: 반복 → **`lastDone`(마지막 완료 시점)만 기록, status 안 건드림**(항목 살아있음); 기존 → 지금처럼 `status=done`. 검증: **반복 항목 완료 → 목록에서 안 사라지고 lastDone 갱신** / **기존 항목 완료 → 여전히 보관함행(Stage 0 net 통과)**. 헤드리스.

**Stage 4 — 다음 회차 + 놓침 + 자동완성.** Core 순수 함수(주기+기준+lastDone+now → 현재 회차 날짜·놓친 회차 수). 완료 시 다음 회차로 당김 + **앱 열 때 catch-up**(`resolve()` 끝, **멱등 가드** — append가 다시 load를 부름). 자동완성(당일 정오/지나면) 적용. 화면에 "N일 놓침" 표시. 검증: Core 함수 테스트(여러 주기·놓침·경계), catch-up 멱등. → **여기까지가 "화면에서 반복이 도는 것".**
  **구현됨 2026-08-03.** 모델: **앵커 = 마감(due) = 회차 시각, 미리 알림(resurface) = 게시 시작(lead).**
  (⚠️ 정정 2026-08-03: 처음엔 "앵커 = 미리 알림"으로 적었으나 lead-time(8시 약·7시 알림)을 담을 칸이 없어 **뒤집었다** — §3-A가 정본.
  이 줄의 옛 "앵커=미리 알림" 서술은 이 정정으로 대체.) **완료 → `max(now, 현재 마감)` 이후 첫 회차로 전진**(온타임·이른·밀림 다 다음 미래 회차 → 게이트가 즉시 숨김, 놓친 날 건너뜀), **미리 알림도 같은 간격 전진(lead 보존).** **놓침 = 오늘 이전 지난 회차 수.** **catch-up = 자동완성 있으면(정오/당일끝) 지난 회차 자동 전진, `none`이면 안 함(쌓임)** — `resolve()` 끝, 멱등. **완료 취소는 lastDone·마감·미리 알림 되돌림.** 놓침 표시: 상세 "N일 놓침" 배너 + 목록 칩(`recurStatusChip`: 놓침/완료 — **회차 기준 `doneThisCycle`, #4 아래 참조**).

**Stage 4 설계 반영 (2026-08-03 조사):**
- **회차 이동 = 완료 즉시 + 앱 열 때, 같은 Core 함수.** 완료 시 다음 회차를 미리 알림에 써 즉시 빠지게(실기기에서 "안 빠진 것처럼 보임" 방지), 앱 열 때 `resolve()` 끝에서 catch-up. 규칙이 갈리지 않게 한 함수(멱등 가드).
- **게시 게이트 재사용(새 장치 없음) — 성립 확인.** 완료 → 미리 알림 = 다음 회차 시각. 완료 직후 미래 → `isPublished` false → 빠짐 / 도래 → 나타남 / 놓침 → 과거 미리 알림 계속 게시 → 쌓임 저절로 성립. **daily/weekly/yearly는 현재 날짜 게이트로 됨.**
- **✅ #3 채택 — 게시 게이트 시각화(2026-08-03 구현).** `isPublished` 미리 알림 분기 `startOfDay` 비교 → `rd <= now`. **시각 지난 항목은 계속 보임(놓친 것 안 숨김) ★, 시각 미래는 그 시각 전까지 안 보임, date-only는 자정부터(불변).** 소비처 1곳, 알림 별개라 영향 없음. 실데이터 7개 중 **지금 보이는 것 사라짐 0**(마감 분기 불변, 미래 2개만 자정→그 시각으로 밀림). `PublishGateTimeTests`.
- **완료한 것이 목록에서 안 보이는 문제(#4).** 완료 후 항목은 '지금 챙길 것'에서 빠져 **'살아있는 기억'(확정 시)** 으로 감. 목록 칩(`recurStatusChip`)이 "완료"/"N일 놓침"을 띄워 해소.

**#4 완료 표시 — 회차 기준으로 통일 (2026-08-03, 실기기 지적):**
- **증상:** 실기기에서 한 항목이 "오늘 완료" 칩 + '지금 챙길 것'에 "지남"을 **동시에** 보였다(모순). 원인 = 칩은 `doneToday`(**lastDone 날짜 == 오늘**, 날짜만), 게이트 `isPublished`는 **마감 시각**까지 비교 → **두 기준이 날짜 vs 시각으로 갈림.** 새벽에 누른 완료(구 빌드, 마감 전진 안 함)가 "오늘(날짜)"=참, "6시 마감(시각)"=미완료로 갈렸다. **경위: Stage 3의 날짜기준 최소판 `doneToday`가 앵커 전환(마감=앵커) 때 갱신되지 않아** 생긴 구멍.
- **해결 = `doneThisCycle`.** **칩·배너·완료버튼·게이트가 모두 같은 기준(마감 앵커)을 본다:** `마감 > now`면 이번 회차 닫힘(= `!isPublished`). 완료해야 마감이 전진하므로 마감이 미래인 것 자체가 증거 → 두 기준이 **구조적으로** 못 갈린다. **세 상태: 마감 ≤ now = 아직 / 마감 > now & lastDone ≥ 직전 회차 = 했다 / 그 외 = 넘어갔다.**
- **`lastDone`은 버리지 않고 "했다 vs 넘어갔다"의 증인.** 마감 전진은 **자동완성(catch-up)**으로도 일어나는데 그건 완료가 아니라 "넘어감" — `lastDone`을 **직전 회차 시각(마감−1주기)과 비교**(날짜 아님)해 실제 완료만 "완료"로 표시. 자동으로 넘어간 것을 "완료"라 하면 앱이 거짓말이 되므로. (이른 완료는 under-claim할 수 있으나 거짓 완료보다 안전. ⚠️ **이 괄호가 값을 너무 싸게 매겼다 — 2026-08-05 D-3에서 대가가 드러났다. 아래 미결 "이른 완료 under-claim의 대가" 참조.**) 놓침 계산·완료취소의 `lastDone` 용처는 불변.
- **매주·매년도 같은 기준으로 성립** — 마감 앵커만 보므로 "정확한 회차 창은 매주·매년은 Stage 4"라던 옛 구멍이 함께 닫힌다.
- **#3 색 위계 (같은 실기기 지적):** 빨강(coral=overdue)은 **진짜 놓침(과거 날짜)에만.** "지남"은 **오늘 마감이 지난 상태만** 뜨고(당일 한정) D-day 버킷 `.today`라 **이미 amber** — 되풀이는 하루 대부분이 "오늘 지남"이라 빨강이면 신호가 상시화돼 죽는다. amber(주의) vs coral(경고) 한 단계 위계를 **일부러 유지**(전 항목 동일, 되풀이 특례 아님). 코드 변경 불필요했음(이미 amber) — 회귀 방지 주석만 `InboxView`에 남김.

**Stage 5 — 알림 전환 (뒤로).** `repeats:true` + 부분 dateComponents, 하루 N회 다중 트리거(id `sb:<id>:<idx>`), **64 예산 반복/일반 분리.** Core `PlannedNotification` 반복 변형. 검증: planner 헤드리스 → 그다음 실기기.

**실기기 확인 (몰아서, Stage 5 후):** 반복 완료 시 안 사라짐 + 다음 회차로 넘어감 / "N일 놓침" 표시 / 자동완성(당일 정오·지나면) / 며칠 안 열다 열면 일괄 catch-up / 반복 알림이 제 주기·시각에 발화(앱 꺼져도) / 반복이 일반 알림을 안 밀어냄. → 확인 목록은 체크리스트 파일로(대화에만 두지 않는다).

**Stage 1·2 결정 (2026-08-02, 사용자):**
- **라벨 = "되풀이"** (코드 key = `recurrence`). 색 앰버 `0xFBBF24` + 심볼 `arrow.triangle.2.circlepath`(6종·주차와 안 겹침).
- **Stage 2 레이아웃 = 별도 "반복 설정" 카드** — 단 **'시간 설정'(마감·미리 알림)이 위, '반복 설정'(주기·자동완성·꺼두기)이 아래.** 이유: 자주 보는 건 "다음이 언제냐"(시간 설정)이고 주기는 처음 한 번; **첫 카드 위치를 다른 분류와 통일**해 눈이 안 헤매게.
- **꺼두기 = 반복 설정 카드 안의 스위치, 단 꺼진 상태는 상세 상단에 바로 표시.** 꺼둔 걸 잊으면 약을 안 챙기게 된다. 성격 구분: **주기·자동완성 = "어떻게 도느냐" / 꺼두기 = "지금 도느냐".**
- **Stage 2 범위:** 주기 = 매일 / 매주 / 매년(요일·월일은 기준 날짜에서). **하루 N회는 후속** — "한 항목에 여러 시각"이라 다중 시각 입력 + 알림 다중 트리거(Stage 5)와 함께 다룬다.

**Stage 3 결정 (2026-08-02, 사용자):**
- **완료 취소 = 완료 버튼이 오늘 상태를 반영하는 토글.** 오늘 안 했으면 "이번 것 했어요"(완료), 오늘 했으면 "오늘 완료됨 ✓"로 바뀌고 옆에 "취소". **취소 = 직전 완료 시점으로 되돌림**(이벤트 이력의 두 번째 최신 lastDone → `Recurrence.priorLastDone`)이라 놓침 계산의 streak가 보존된다(오늘 것만 무르고 어제까지는 남김). 항목 그 자리에서 되돌린다(보관함 안 거침).
- **"오늘 했나" = 지금 최소판만.** idempotency(두 번 눌러도 토글이라 안전)와 "오늘 약 먹었나" 표시가 Stage 3의 핵심이라 필요. 최소판 = `doneToday` = **lastDone의 날 == 오늘**(매일 약 커버). **주기별 정확한 회차 창(매주·매년 window, 다음 회차 날짜)은 Stage 4.**
  - ⚠️ **폐기(2026-08-03):** `doneToday`(날짜 기준)는 앵커 전환 후 게이트(시각 기준)와 갈려 #4 모순을 냈다. **`doneThisCycle`(마감 앵커 기준)로 대체** — 위 "#4 완료 표시" 참조.
- **문구:** 되풀이 완료 = **"이번 것 했어요"**(오늘 했으면 "오늘 완료됨"), 스와이프는 짧게 **"했어요"**. 삭제 = 되풀이일 때 **"되풀이를 그만둘까요? 기록도 함께 삭제돼요" / 버튼 "그만두기"** — 그만두기(삭제) ≠ 잠시 멈춤(꺼두기) ≠ 이번 것(완료) 셋을 구분.
- **lastDone 형식 = 시각 표준형(T, `dayTimeString`)** 그대로(분 정밀, 시각 조각과 일관).

  `doneThisCycle`은 `lastDone ≥ 직전 회차`를 요구하므로 **마감 시각 전에 완료하면 판정이 "안 했다"** 가 된다(의도된 under-claim, 거짓 완료 회피). 그런데 그 판정이 **화면·행동을 함께 되돌린다:**
  - **`[이번 것 했어요]` 버튼이 돌아오고 `[취소]`가 사라진다.** 누른 직후엔 안 보인다 — `DetailView`가 `cycleDoneLocal = true`를 낙관적으로 세우므로. **상세를 닫고 다시 열면** `doneThisCycle`로 재계산돼 버튼이 돌아온다. (실기기 확인 2026-08-05: 버튼 돌아옴.)
  - **(a) 다시 누르면 회차가 또 전진한다 — ✅ 해소(2026-08-05, 후보 ②로. 아래 §5-대가).** `completionAdvance`의 `pivot = max(now, 마감)`은 마감이 이미 미래여도 **정확히 1회차 더** 전진시킨다. 계측: 마감 08-05 → 1차 완료 **08-06** → 2차 완료 **08-07**. **하루가 조용히 사라진다.**
    → 실사용: **8시 약을 7시 30분에 먹고 눌렀다가 상세를 다시 열어 또 누르면 내일 약이 목록·알림 양쪽에서 없어진다.** 자동완성 `none`(약)이라 catch-up도 안 되돌린다. **"약을 3일 놓친 것"이 이 설계의 출발점인데, 이른 완료가 정확히 그 경우를 만들 수 있다.** Stage 5-C가 다루는 "놓친 되풀이 침묵"(§9)과 같은 종류의 구멍이고 방향은 반대다.
  - **(b) 이른 완료를 되돌릴 수 없다.** `취소`는 `cycleDoneLocal`일 때만 그려지므로, 다시 연 화면에서는 무를 길이 없다(§5 "완료 취소 = 토글" 결정이 이 경우엔 성립하지 않는다).
  **(a)는 고쳤고 (b)는 남는다 (2026-08-05).** 후보 ②(**표시는 그대로, 재완료만 멱등**)를 택했다 — 데이터 유실을 먼저 끊되 "완료"의 정의는 안 건드리는 길이다. 구현·근거는 **§5-대가**, 그물은 `RecurrenceRecompleteTests`.
  **남은 후보는 (b)용이다:** ① `doneThisCycle`을 `lastDone`이 **현재 회차 창 안**이면 참으로(= 이른 완료도 "했다"로 인정, 자동 전진과는 여전히 `lastDone` 유무로 갈림) ③ `취소`를 판정과 분리해 **`lastDone`이 있으면 항상** 그린다. **①은 "완료"의 정의를 건드리므로 여전히 §5 결정 사항이다.**
  **→ 두 후보를 코드로 재봤다: §5-조사 (2026-08-05, 결정 아님).** 요지: **①·③ 어느 쪽도 단독으로 (b)와 "눌러도 반응 없는 버튼"을 함께 못 닫는다.** 소박한 ①은 **넘어간 회차를 "완료"라 부르고**(계측으로 확인), 가드를 붙인 ①은 **완료 표시가 회차 시각에 만료된다.** ③은 표시를 못 고치면서 **`취소`가 자동 전진까지 되돌리는 버튼**이 된다. 갈림길은 **"닫은 회차를 기록할 것인가"** 하나로 좁혀졌다.
  ⚠️ **(b)를 정할 때 §5-대가가 적어둔 "눌러도 반응 없는 버튼"을 함께 본다** — 뿌리가 같아 따로 고치면 두 번 손댄다.
  (**결정 2026-08-05: `second-brain-v0-spec.md` 반영은 (b) 방향이 정해질 때 이 절과 **함께** 한다** — (a)만으로는 반쪽 반영이라 아직 안 넣는다. 사용자 승인.)

## 이번에 하지 않기로 한 것 (미결로 기록)

- **총 완료 횟수** — 이번에 넣지 않는다. 완료할 때마다 1씩 올리는 방식은 **필드별 LWW**라 두 기기에서 각각 올리면 한 번이 사라진다(5→6, 5→6 → 병합 결과 6). 정확히 세려면 **완료 이력이나 놓친 이력**을 남겨야 하는데 그건 별건. **몇 주 써보고 필요하면 그때** 정한다.

- **일정의 시작·끝 시간(O1)과의 관계** — 반복 분류도 나중에 그 칸들을 쓰게 할지는 **그때 정한다.**
